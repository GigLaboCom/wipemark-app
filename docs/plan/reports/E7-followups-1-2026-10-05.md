### W1 — no epic number in a catalogue value

The test walks every message and term of every catalogue, every selector
variant included, through `fluent_syntax`. It checks the values only;
comments keep their epic ids. The pattern `\bE\d+(-\d+[a-z]?)?\b` is
matched by hand, because the crate takes no regex engine for one test, and
a second test pins what the matcher finds and what it does not:

- found: `E4-6b` and `(E7)`;
- not found: `E7a`, `U+200E` and `Excel`.

No existing value matches, so the allow-list is empty.

### W3 — the log line

A scoped `tracing` subscriber captures three clean lines:

1. a clean beside a file in a folder whose names are distinctive;
2. a `SameFile` refusal;
3. a kept paste.

None carries a path component, a file name or a word of the document. A
path's shape is now logged through `Elided`'s `Display` (`written=<elided

One thing had to be fixed in the test harness itself. With exactly one

with no subscriber, cached "never", and the capture saw nothing (about one
run in three). A second dispatcher, kept for the life of the test binary,
keeps the interest open. It is commented where it is made.

### W4 — C2PA alone (D281)

The task asked to check that `has_ai_metadata()` is false on
`c2pa-jumbf.jpg`, or the test proves nothing. It is **true**, and it can
never be false:

- `wipemark_image::MetadataKind::is_ai_provenance` includes `C2pa`
  (`crates/wipemark-image/src/lib.rs:190`);
- `MetadataFinding::is_ai_provenance` is true for any finding with
  evidence (`:259`);
- `is_c2pa` is true for kind `C2pa` or C2PA evidence (`:263`).

So every C2PA finding is AI provenance, and `has_c2pa()` implies
`has_ai_metadata()`. The clause `|| seen.metadata.has_c2pa()` in the look
could not change its answer: H12 is an **equivalent mutation**, and no
test can make it red.

The look now reads `has_ai_metadata()` alone. That is the rule the clean's
verdict reads (`removed.any(is_ai_provenance)`), so the two agree by
construction. The new test pins on the real file what the look relies on:

- every provenance finding on `c2pa-jumbf.jpg` is C2PA;
- there is no XMP on it;
- the look says AI metadata;
- the clean says `Cleaned`.

The meaningful mutation, W4/M1, makes the look ignore a C2PA-only picture
(`&& !has_c2pa()`) and goes red. The clean's own `|| still_has_c2pa` stays
as it was, and H4 guards it through constructed reports.

### W5 — `PICTURE_LIMIT`

Two tests guard the limit:

- **The stat.** A sparse PNG one byte past the limit (`set_len`, no
  64 MiB on disk) is refused `TooBig` with its size on the `stat`. No
  report is produced, so no layer ran. The look refuses it the same way,
  and nothing is written.
- **The read.** For the stat and the read disagreeing, a FIFO plays a file
  that keeps growing (`mkfifo`, Unix only). The stat says 0 bytes, the
  writer sends 66 MiB, and the clean is refused at `limit + 1` bytes read.

W5/M2 removes the read-side check and goes red.

### W7 — one line, and no clobbering (D283, D284)

**One line per application.** The new `apps/wipemark-app/src/cleaner.rs`
is a GPUI global entity over the pure `Line`, which moved out of
`queue.rs`.

- The queue's Clean, Clean all, `--clean=` and Replace, and the panel's
  Clean, all `ask` it.
- It runs one clean at a time, first asked first done, with the plan
  taken at each clean's start.
- It emits `Started` and `Finished` events, which move a row from Queued
  to Cleaning to done and fill the panel's lines.
- The status bar's count and the panel's "Cleaning…" read
  `progress()` and `pending()`.

The test asks for the same file twice from the line, as the queue and the
panel would, a click apart. The result is one `Cleaned` and one `Exists`,
in that order, with one file written.

**Across processes.** `wipemark_intake::inplace::write_new` stages the
result in a temporary file, then publishes it with
`hard_link(temporary, destination)` and removes the temporary name. The
operating system refuses the link with `AlreadyExists` when anything has
the name: a file, or a dangling link. Where hard links are refused, a
`create_new` (`O_EXCL`) copy takes over. It refuses a taken name too, but
it is not atomic, and is removed if the copy fails part way.

`replace` sets the original aside the same way: `hard_link(file,
name.original.ext)`, then the result's rename over the file. A failed
write now only removes the second name. The file never moved, so it
cannot be stranded.

Only on a file system without hard links is the old check-then-rename
still the road. The module doc's "The race this accepts" section is
replaced by "No clobbering, between processes too", which says exactly
that. `clean::write_new` uses `inplace::write_new` for every new result, with
no check before it. `write_atomically` is kept for the one file Replace
names.

### W9 — parity with the CLI's own code (D285)

`fixtures/clean-parity/table.tsv` lists twelve inputs:

- six small texts made for the table: two Markdown files, UTF-16 with a
  BOM, a soft hyphen, a homoglyph, and a TIFF head (in a new
  `fixtures/clean-parity/`, marked `-text -diff`);
- six of `image/`'s pictures.

For each input the table gives the CLI's exit, whether the CLI writes, and
whether a window writes. The declared deviations (D260, D262, D263) are
named in it. Two tests read the table and share no code:

- `apps/wipemark-cli/tests/parity.rs` runs the **real binary**
  (`CARGO_BIN_EXE_wipemark-cli`) over every row.
- `clean::tests::the_windows_clean_to_the_clis_table` runs `clean_one`
  over the same rows. It maps an outcome to the CLI's exit: for a text,
  whether Layer A found something suspicious; for a picture, by verdict.

Each side holds its written bytes to the library's answer at the CLI's
defaults. A change to either side's exit or write rule is red on that side
until the table changes, then red on the other side until it follows.
W9/M1 and M2 change the CLI's picture and text exits; W9/M3 and M4 change
the window's verdict and write rule. All four go red.

**Why this way.** There were two other options:

- **Move the policy into a library both applications depend on.** This
  would edit the CLI's sources and move a rule the CLI owns out of it.
- **Run the CLI's binary from an app test.** Cargo builds no other
  package's binary for a test, and a nested `cargo build` would wait on
  the build-directory lock the running `cargo test` holds.

A shared table gets the same teeth with neither problem. The hand-written
tests (`a_text_comes_to_what_the_cli_says_it_does`, `a_picture_…`) stay as
unit tests of `outcome_of`.
