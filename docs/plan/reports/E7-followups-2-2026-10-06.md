### X1 — the queue's crash recovery (D286)

`redeliver` (`crates/wipemark-queue/src/deliver.rs`) has a new arm: when
the file is still there, does not hold the result, and **is the
set-aside**, the delivery is finished with `inplace::write_atomically(path,
&bytes, Some(&original))`, as the `NotFound` arm finishes the rename road.
The rename replaces only the file's name; the original keeps its inode
under `name.original.ext`.

"Is the set-aside" is `is_the_set_aside`: `inplace::same_file` (one inode,
on Unix) **or the same bytes**. That is the decision the task asked for:

- **Off Unix, `same_file` cannot see a hard link.** It compares canonical
  paths there, and two links have two. Std's stable API has no file
  identity on Windows (`MetadataExt::file_index` and
  `volume_serial_number` are behind the unstable `windows_by_handle`), so
  giving `same_file` a non-Unix answer would mean `unsafe` FFI or a new
  dependency in a crate that has none.
- **The bytes see it everywhere, and lose nothing.** If the file holds
  exactly the set-aside's bytes, the original is whole under its second
  name whatever the inode, and writing the result over the first name is
  what the delivery was going to do.

The doc comment now names both roads. The test builds the crash state
five ways: set aside by a **hard link** (the state D284 leaves — probe
A's), by a **rename**, and as **the same bytes under two files** (what a
hard link looks like where the inode cannot be seen) — all three
`Delivered`, the file holding the result, the set-aside the original;
"written, not yet recorded" as before; and "someone else's bytes", still
`OriginalExists`. X1/M1 deletes the new arm (red on the link and copy
cases); X1/M2 drops the bytes comparison (red on the copy case — on Unix
the inode alone would hide it).

### X2 — the FIFO test cannot hang (test only)

The writer thread now tells a channel when it is done, opened or not, and
the test waits for it through `release`: up to ten seconds, opening and
closing the pipe's read end with `O_NONBLOCK` every 100 ms. A writer still
blocked in `open` is released by that open; a writer that never finishes
is a failed assertion naming it — "the pipe's writer never got its reader:
the clean did not read the pipe" — never a wait. `O_NONBLOCK` is spelled by
hand (`0o4000` on Linux and Android, `0x0004` elsewhere); the application
does not take `libc`.

With H39's change (`!metadata.is_file()`), the clean refuses without
opening the pipe, `release` lets the writer through, and the test fails on
the verdict: X2/M1 is **red, not HANG**.

**A question rather than a change: should the clean refuse what is not a
regular file before opening it?** H39's hardening is reasonable in
itself — a FIFO, a socket or a character device dropped on a window is
not a document, and reading one can block a background thread until
something writes to it. But it would retire this test's way of making a
file grow under the read, and the read-side limit check (D264) would then
need another way to be tested (a file appended to by a second thread while
it is read, which is racy). Left as it is; the owner's call.

### X12 — a clean that panics (D288)

The cleaner runs each clean under `std::panic::catch_unwind`
(`AssertUnwindSafe`) on the background executor; a panic becomes
`clean::panicked(id)` — `Verdict::Failed(Failure::Panicked)` with the one
log line every clean leaves (`why` "panicked"); the panic hook still logs
the panic itself — and `finished` is called either way, so the next clean
starts. `clean-failed-panicked` in en, ru and de says the clean stopped on
a fault in this version and the log has it, and asks the person to look
where the result would go before cleaning again: it does **not** say
nothing was written, because a panic can fall after a write.

The seam is the `Cleaner`'s `run` field (a `fn`, `clean_one` or
`replace_one` by default). The `#[gpui::test]` hands it one that panics on
`panics.md`, asks for `panics.md` then `after.md`, and reads
`[Failed(Panicked), Cleaned]`, `after.cleaned.md` on disk and an idle line.
X12/M1 removes `catch_unwind`: the panic reaches the test scheduler and the
test fails — red, not HANG.
