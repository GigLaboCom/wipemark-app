## What was done

### `measure_at` (`crates/wipemark-pixels`)

```rust
#[doc(hidden)]
pub fn measure_at(
    raster: &Raster,
    profile: &Profile,
    map: &AlphaMap,
    rect: SubRect,
    kernel: Kernel,
) -> Option<Outline>
```

`verify::outline`'s own code over a rectangle **nothing was restored in**:
it builds the template as `verify` does (`template_and_noise`: the map
brought to `rect` by `kernel`, its capture noise taken out) and calls
`outline` with a `Verified` it never hands out. No arithmetic is restated.
`outline` reads five things a restoration would have had; two of them stand
in for the restoration:

* **The contour the mark had** — the share's denominator, `E(0)` before a
  restoration. Here: the contour energy of this template **drawn here** with
  the profile's logo — `restore::composite`, rounded as a file stores it,
  over a copy of the rectangle and its one-pixel ring (all `Grid` reads),
  through `Grid::energy(0)`. That is the stored file a perfect restoration
  would have started from, so the share is what such a restoration would be
  told. (`E(0)` of the clean raster itself is another quantity: on the
  first test case it gives 0.706 where the restoration says 0.0032 — the
  third red check below.) Template values are clamped to [0, 1] for the
  drawing only, as `resampled` clamps them; at a row's own size they are
  already.
* **The pixels the restoration changed** — the set `texture` is taken over.
  Here: the map's support, `α` from `NOISE_FLOOR` to under the profile's
  `opaque_above`, the pixels a restoration of this map would write. It is
  the very set `outline` takes after a real restoration (`steps`, the
  `rough_mark` set), which counts the faint pixels the inverse rounds back
  to themselves (`docs/architecture/visible-marks.md`, D250): so nothing is
  redefined, and the code says so in `measure_at`'s doc.

**How it differs from the document's `measure_at(raster, map, rect,
fidelity) -> Outline`:**

1. **A profile beside the map**: a map has no logo and no opaque threshold,
   and `outline` reads both.
2. **A kernel**: `outline` measures the template, and a template is the map
   brought to a sub-pixel rectangle *by a kernel* (D238). `measure_clean`
   passes `Kernel::Area` at whole pixels, which at a map's own size is the
   map.
3. **No fidelity**: `outline` does not read one. Fidelity enters only in
   `restore`'s `texture_left = source == Lossy && outline.textured()` (and
   the same line in `planar.rs`), and the caller applies it — the example
   does, and the §5 test holds that line equal to the product's.
4. **`Option`**: `None` when the template does not fit `rect` or the
   picture, as `verify` answers no blend there.
5. **`Outline` is now `pub`** (it was `pub(crate)`), re-exported
   `#[doc(hidden)]` beside `measure_at`, so the caller has `left()` and
   `textured()` — the product's verdicts, not a restatement.

* `crates/wipemark-pixels/src/verify.rs:576–580` — `Outline`'s doc comment

### `measure_clean` (`crates/wipemark-picture/examples/measure_clean.rs`, D501)

Its header says what it is for, what it does, how to run it, what it needs
and what its output means. In short:

```sh
cargo run --release -p wipemark-picture --example measure_clean -- files --out rows.jsonl [OPTIONS] <picture>…
cargo run --release -p wipemark-picture --example measure_clean -- list  --out rows.jsonl [OPTIONS] <list.tsv>
cargo run --release -p wipemark-picture --example measure_clean -- synth --out rows.jsonl [OPTIONS] [--side 1100]
cargo run --release -p wipemark-picture --example measure_clean -- summarise <rows.jsonl>…
# OPTIONS: --profile ID (repeated; every shipped one) --map ID --count N (100) --seed S (1) --pad P (8) --skip-rows
```

* **Decoding**: `wipemark_picture::decode_with_planes` (the container from
  `wipemark_image::inspect`), with the decoded fidelity and planes.
* **What is avoided, and how**: the product's own examination runs first —
  `wipemark_pixels::examine_with(raster, planes, shipped, {source:
  fidelity, profiles: None})` — and the rectangle of every **finding**,
  proved or refused, is avoided: a drawn rectangle whose box grown by
  `--pad` (8, the farthest any measure reads: `texture_around`'s band is 2–8
  pixels out) meets one is drawn again (counted, "draw(s) refused"). A
  proposal the second proof calls **no blend** is not a finding and
  `examine` does not hand it out (D235), so it is not avoided: by the
  product's measure it is not a mark. `--skip-rows` also avoids every row of
  every profile that answers for the picture's size — for a picture known to
  carry a mark the examination may miss (S11's 1024 crop), and on the host's
  Gemini originals as a second fence.
* **What is drawn**: per profile, the map the product would use at this
  size — the first row whose `when` matches, at that row's size; the
  search's map at its own size when none does; `--map` names one — at
  whole-pixel places, uniformly, at least 8 pixels from the edge (every
  ring whole), `--count` per picture and profile (100), from a xorshift
  generator (the pixels suite's `Rng`) seeded with `--seed ^` the first eight
  bytes of the picture's sha256 `^` those of the profile id's: the same
  picture gives the same rectangles whatever else is on the command line.
* **Output**: one JSON line per rectangle (the fields are in the header,
  `left`/`textured` the product's `Outline::left()`/`textured()`,
  `texture_left` the latter on a lossy source as `restore` applies it), and
  a Markdown summary per profile × fidelity over every group, then per
  group: per measure n, p50, p95, p99 (nearest rank, `verify.rs`'s
  `percentile`), max, the constant, p99 / constant, the share over the
  constant, and §4.1's arithmetic — p99 + 20 % (`RULE_MARGIN` `[tunable]`)
  and how far that lands from the constant; then how many rectangles the
  product would say left.
* **Why more lines than "a p50/p95/p99 per measure"**: three of the five
  bounds are not a constant alone — `left()` says a step over
  `max(STEP_LEVELS, spread)` and a colour over `max(CHROMA_LEVELS,
  chroma_spread)`, `textured()` a roughness over `max(TEXTURE_LEVELS,
  TEXTURE_RATIO × texture_around)`. Over all rectangles of real content the
  raw `|step|` has a p99 of 15–37 levels against a constant of 1, which says
  nothing about the constant. So each such measure is given three ways: over
  every rectangle; over the rectangles where the constant is the bound that
  binds (`spread ≤ STEP_LEVELS`, `chroma_spread ≤ CHROMA_LEVELS`,
  `TEXTURE_RATIO × around ≤ TEXTURE_LEVELS`; the ratio where `texture >
  TEXTURE_LEVELS`); and as a **margin**, the value over its whole bound, 1 at
  the bound. The margins restate the three tests for the summary only and
  are held to the product's verdicts by a test.
* **`synth`**: the pixels suite's thirteen procedural backgrounds and two
  night skies (`tests/support/mod.rs`, borrowed by `#[path]` as
  `tests/lossy.rs` does), 1100 square, each as it is (lossless) and through
  `wipemark_pixels::synth::jpeg_planes` at 4:4:4 q95 and 4:2:0 q95 and q90
  (lossy, with the planes) — an IJG encoder's planes and their decode, never
  a file, "a JPEG, not the JPEG Pillow writes" (its own doc). Groups are
  `synth:<kind>:<variant>`.
* `[[example]] test = true` in `crates/wipemark-picture/Cargo.toml`, so its
  tests run with `cargo test -p wipemark-picture`.

No Python summariser was added: `summarise` pools JSON lines in the example
itself, so the figures and the summary are one program.

**The null restoration.** The document asks for "`restore` of a
zero-opacity profile". The code allows no such thing: a profile at zero
opacity has no support, `verify` calls it no blend before anything is
measured, and only `verify` builds a `Verified` (a `compile_fail` doctest
holds it). The null restoration the code allows is this one: a clean
picture `P` is the restoration of a composite of a procedural picture (the
mark `drawn(map)` at its row's own place); composited again where it was,
the very bytes come back (`again == first`, asserted), and restored again,
`P` comes back **to the byte** (`again == clean_picture`, asserted). What
`outline` measured after that restoration, `measure_at` measures over `P`
with nothing restored. (A case on the glyph sheet `Kind::Glyphs` was dropped:
V1's mark on it is refused by its edges, so there is no restoration to
compare; `Kind::Checker` likewise for V2. `Kind::Flat` stands in.)

## Deviations from the document and the task

1. **`measure_at`'s signature** is `(raster, profile, map, rect, kernel) ->
   Option<Outline>`, not `(raster, map, rect, fidelity) -> Outline`; the five
   reasons are above. `Outline` became `pub` (hidden) for it.
2. **The null restoration** is a restoration of a composite that hands the
   clean picture back to the byte, not a zero-opacity profile, which the code
   cannot restore (above).
3. **The document's mutation** (texture in RGB) cannot turn the equality
   test red when it is made in the shared code path — both sides move. It
   was made twice: in the shared path (red: the grain test) and on
   `measure_at`'s side alone (red: both tests). The second is the
   protection the §5 row names, "`measure_at` restates nothing".
4. **The share's denominator** is the contour of the template drawn on the
   rectangle, not the rectangle's own contour; the document does not say,
   and the other choice is not the same quantity (0.706 against 0.0032).
5. **The summary** gives each conditional bound three ways (every
   rectangle, where the constant binds, the margin), beyond "p50/p95/p99 per
   measure against today's constants", because the raw distribution of a
   bound `max(constant, spread)` says nothing about the constant.
6. **Proposals that are no blend are not avoided**: `examine` does not hand
   them out (D235). Findings are, proved or refused; rows with
   `--skip-rows`.
7. **The synthetic JPEGs** are `synth::jpeg_planes` in memory (IJG maths in
   reals, no entropy code, not Pillow's bytes), measured with their planes,
   not files through `decode`.
8. **`regress.py list`** was added beside `--golden`, and `.gitignore`
   gains `/golden/*/cache/`.
9. **Line numbers** in the document (`verify.rs` 218, 495–600, 605) are
   `4b5ba17`'s; at `0696501` they are 223, 526–579, 632 (above).
10. **"R2 §2"** in the task is R2 §4.2 in its document.
