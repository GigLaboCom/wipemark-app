## What changed, per item

### 1. A key that cannot be sent is refused when it is saved

* **The rule** is `wipemark_engine::http::wire::authorization(&Secret) ->
  Result<String, KeyFault>`: the one builder of the `Authorization` value
  and still the one `Secret::expose` outside the vault crate. A token is
  visible ASCII, `!`..=`~`, at least one character; `KeyFault` is `Empty`,
  `NotAscii`, `Control`, `Space` (an inner space or tab — `Secret` already
  trims the outer ones). `http::sendable(&Secret)` is the same function
  with the header thrown away, public for the window.
* **The transport** builds the header once in `wire::exchange`, before the
  retry loop and before any socket, and refuses an unsendable key as
  `EngineError::Transport("the stored key has a character that is not
  ASCII; nothing was sent")` — a key stored before this rule existed.
  `Unavailable` (in `lib.rs`) was outside this batch's reach, so it is not
  a structured refusal; see "Decisions" below.
* **The window.** `engine::admit_key` (the rule), `engine::save_key(&Vault,
  account, &Secret) -> KeySaved { Stored | Refused(KeyFault) | Failed }`
  (the rule, then `Vault::set` — the whole of Save, run on the background
  executor) and `engine::key_refusal_message`. `Preferences::store_key`
  asks `admit_key` on the click: a refusal sets `key_refused`, notifies and
  returns — no spawn, no vault, no lookup orphaned, the stored key (if
  any) untouched. `key_refused` is cleared by the next lookup, a good Save
  and Forget, and painted under the state line in the danger colour. The
  field still empties on Save either way (write-only).
* **Catalogue:** `settings-engine-key-refused-{not-ascii,control,space,empty}`
  in en-US, de, ru.

### 4. Setting the original aside lives in a library

`unsafe` or a dependency).

### 5. The same seed after a cancel — investigated, the server's

Finding: **not the cancel, not the slots, not our client — llama-server's
prompt cache.** A prompt the server has cached is not evaluated again
(only the tail after the longest cached prefix, or the last token alone
when all of it is cached: "need to evaluate at least 1 token … n_past was
set to 26"); the last position's logits then come from a batch of another
size, differ in the low bits, and at temperature 0.9 sometimes sample a
different token. A cancel matters only because it leaves the slot holding
a *different* prompt, so the next request is evaluated from the shared
system prefix instead of restored whole. With the cache off (`cache_prompt:
false` in the body, or `--no-cache-prompt` on the server) every request
agreed. Written up as "Reproducibility" in `docs/architecture/remote-engine.md`.
**No code fix**: `cache_prompt` is llama.cpp's own field, a server that
rejects unknown fields would refuse every request (D59's reason for not
sending `min_p`), and the cache is what saves E4's second candidate the
cost of the prompt. The live test's "does not reproduce" line now names
the likely cause.

Commands (`$S` the scratchpad; the scripts are `$S/tails1-seed.py`,
`$S/tails1-seed2.py`): one fresh
`$S/llama-server-build/bin/llama-server -m $S/models/Qwen3-4B-Instruct-2507-UD-Q4_K_XL.gguf --port 18091 -c 4096 --alias qwen3 -np {1|2}`
per row; per server six streamed `POST /v1/chat/completions` with the body
`HttpEngine` sends — `{"model":"qwen3","stream":true,"messages":[{"role":"system","content":"You are a terse assistant."},{"role":"user","content":"Write two sentences about a lighthouse."}],"temperature":0.9,"top_p":1.0,"max_tokens":64,"seed":1234[,"cache_prompt":…]}` —
in the order: twice cold; a streamed "Write a long story about a lighthouse
keeper." (`max_tokens` 2000) dropped after its first piece, then twice; a
completed "Say hello." (`seed` 7, `max_tokens` 8), then once; another
dropped stream, 3 s, then once.

A = "A lighthouse stands tall on a rocky cliff, its bright beam cutting
through the fog to guide ships to safety. Its steady glow has been a
