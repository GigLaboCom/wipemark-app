**Verdict.** Done. `--features native` links the prebuilt release `b10731`
of `GigLaboCom/llama-cpp-prebuilt` by default on the four published
targets; the source build is one environment variable away and has a CI
lane of its own. The engine is unchanged: the same live gate passes at the
E2-4 rate through the prebuilt libraries, and the archive's bindings are
byte-identical to what bindgen generates here and on the runner. CI's
`native` job went from 10–15 minutes to 2 min 19 s cold and 50 s warm.

The four archive sha256 the task gave were checked against the release
before being written anywhere: `curl` of each asset and `sha256sum`, equal
to the task's values and to the release's `SHA256SUMS`.

## What was built

1. **A source of llama.cpp** (`crates/wipemark-llama-sys/build.rs`,
   `native::origin`): `WIPEMARK_LLAMA_SOURCE=1` → source;
   `WIPEMARK_LLAMA_PREBUILT=<dir>` → that unpacked archive; a published
   target → the release; any other target → source with a warning. Both
   variables set is a build error. (I1)
2. **The pin in one file**, `src/pin.rs`, compiled into the crate
   (`wipemark_llama_sys::pin`) and into `build.rs` (`#[path]`): the commit,
   the tag, ggml, `PREBUILT_REPO`, `PREBUILT_TAG` and `PREBUILT_SHA256` for
   the four targets. `build.rs` no longer holds its own copy of the commit.
   `PIN.md` names the release, the run that built it and the four sha256;
   its bump procedure gains step 7 (the release, then the sha256).
3. **The release, checked** (`mod prebuilt`): `curl` into a `.part`, the
   sha256 compared with the pin **before** unpacking, `flate2` + `tar` into
   a temporary directory, the layout and `PROVENANCE.txt` (`llama.cpp_commit:`
   = the pin, `target:` = `TARGET`) checked, `archive.sha256` written, one
   `rename` into the cache. No fallback to a source build on any refusal.
4. **The cache** `<profile>/llama-cpp-prebuilt/<sha256[..12]>/llama-cpp-b10731-<target>/`
   (`target/debug/…`), with `archive.sha256` beside the root, checked
   against the pin on every use. An override outside the profile directory
   is reached through `local-<fnv64 of the path>`, a symbolic link in the
   cache. (I2)
5. **Bindings**: the archive's `bindings.rs` copied to
   `$OUT_DIR/bindings.rs` (prebuilt); bindgen as before (source). A source
   build that finds the archive in the cache copies its bindings beside
   bindgen's and compiles `the_archive_bindings_are_the_ones_bindgen_generates`
   in (byte comparison first; then the code with comments, attributes and
   layout assertions dropped). (I4)
6. **Backends and linking** shared by both roads (`native::emit`):
   `BACKENDS_DIR` = the archive's `backends/`; the rpath and `cargo:lib_dir`
   = its `lib/`; no `-Wl,-rpath` for a Windows target (here and in the two
   applications' `build.rs`); on Windows the three DLLs (`bin/` of the
   archive, `OUT_DIR/bin` of a source build) copied into `<profile>/`,
   `deps/` and `examples/`. `GGML_*` variables are named as ignored in
   prebuilt mode. (I5, I6)
7. **MSVC Release flags** in source mode (`source::msvc_release_flags`):
   `CMAKE_{C,CXX}_FLAGS_RELEASE=/O2 /Ob2 /DNDEBUG` defined, `/DWIN32
   /D_WINDOWS` and `/EHsc` added; `scripts/check-msvc-flags.sh` reads both
   configure lines back from the build script's stderr. ASM flags are left
   as the crate sets them: ggml compiles no assembly with MSVC. (I7)
8. **CI** (I8): `gate.yml` `native` and `macos` prebuilt — no `fetch.sh`, no
   cmake, clang or `glslc`; `native` installs `libvulkan1
   mesa-vulkan-drivers` only and prints the ggml devices; `macos` also runs
   `standalone.rs` under `llama-native` (the archive's dylibs are `@rpath`
   install names). New `llama-source.yml`: Linux source + Vulkan with the
   bindings compared, Windows prebuilt (a test binary run with an empty
   `PATH`) then MSVC source with the flags read back; on changes under the
   two llama crates or the workflow, weekly (Monday 04:17 UTC), and by hand.
9. **Documents**: `docs/architecture/local-engine.md` (a new section, "Where
   llama.cpp comes from"; the features table, the backends, the rpath, the
   native-gates recipe), `PIN.md`, `vendor/README.md`, `vendor/fetch.sh`'s
   header.

New build-dependencies, all optional under `native`: `sha2` and `flate2`
(already in the lock), `tar` 0.4.46 (new, with `filetime`; `xattr` off).
`Cargo.lock` gains the `tar` package only.

## Design choices, and why

| | choice | why not the alternative |
|---|---|---|
| I1 | the switch is the environment (`WIPEMARK_LLAMA_SOURCE`, `WIPEMARK_LLAMA_PREBUILT`) | "source on a target nobody publishes" depends on `TARGET`, which a feature cannot express; a feature would be forwarded through four crates; `GGML_*`/`CMAKE_*` already choose the source build's shape the same way. Cost: `bindgen` and `cmake` are compiled (never run) in a prebuilt build — no libclang needed, `bindgen` loads it at run time |
| I2 | cache under the profile directory, keyed by the sha256 | cargo puts a link-search directory on a test's loader path only under the profile directory (a probe crate: `target/debug/x` kept, `target/x` and `/tmp/x` dropped), so a dependent's test finds `libllama` with no rpath of its own; `$CARGO_HOME` or a user cache would be outside it and survive `cargo clean` as garbage |
| I3 | `curl` subprocess + `sha2`/`flate2`/`tar` | `ureq` + rustls (in the lock) would compile a TLS stack for the host again inside a build script to fetch one file; `tar.exe` on Windows is bsdtar but Git's GNU tar may come first on `PATH` and reads `C:` as a host |
| I4 | copy the archive's `bindings.rs` into `OUT_DIR` | `lib.rs` keeps one `include!` path; `ffi` compiling against it is the API check |
| I6 | Windows DLLs copied beside cargo's executables | the Windows twin of the rpath; `PATH` alone would leave a built `wipemark.exe` unable to start outside cargo — the failure `standalone.rs` exists for |
| I8 | the source lane on a path filter + weekly + dispatch | the source build changes only with the sys crate (and the runner image, hence weekly); on every push it would put the quarter-hour back |

## Proposed decisions (for README §4)

| # | decision | why |
|---|---|---|
| D226 | `wipemark-llama-sys` (`native`) links the prebuilt release of `GigLaboCom/llama-cpp-prebuilt` for the pin by default on the four published targets; the cmake + bindgen build stays, for `WIPEMARK_LLAMA_SOURCE=1` and every other target. Revises D46's "cmake + bindgen" and D48's fetch (now source-only) | 10–15 CI minutes and a C++/Vulkan toolchain on every machine, for libraries built identically each time |
| D227 | The switch is the environment, not a feature | it depends on the target; no forwarding through four crates |
| D228 | An archive is checked against the sha256 pinned in `src/pin.rs` before unpacking, and every root (override included) against `PROVENANCE.txt`'s commit and target; a refusal never falls back to a source build | "these are not the bytes" must not become "the build took fifteen minutes" |
| D229 | The cache is `<profile>/llama-cpp-prebuilt/<sha12>/`, with `archive.sha256` checked on every use; an override outside it is reached through a symlink in it | cargo's loader path covers only the profile directory |
| D230 | The fetch is a `curl` subprocess; `sha2`, `flate2`, `tar` are the only new build-dependencies | no TLS stack compiled into a build script |
| D231 | Prebuilt bindings are the archive's; a source build with the archive cached compares the two | one API for `ffi` on both roads |
| D232 | No rpath for a Windows target; the DLLs are copied beside cargo's executables | Windows has no rpath; `standalone.rs`'s rule on Windows |
| D233 | A source build for MSVC defines CMake's Release flags itself (`/O2 /Ob2 /DNDEBUG`, `/EHsc`) | the `cmake` crate's Visual Studio branch replaces them |
| D234 | CI: `native` and `macos` prebuilt; `llama-source.yml` (Linux + Vulkan, Windows MSVC, Windows prebuilt) on the llama crates' paths, weekly and by hand | the source road must not rot, and must not cost every push |

## Open

- `aarch64-unknown-linux-gnu` is pinned and never linked here: no CI job
  runs on an arm64 Linux runner. The producer smoke-tested that archive.
- The Windows prebuilt road is proven model-free only (no GPU, no
  `vulkan-1.dll` on the runner); a Windows live gate needs a Windows
  machine with a GPU.
- `rust-cache` does not keep a workspace member's `OUT_DIR`, so every CI
  run downloads the 22 MB archive again (about a second) and the source
  lane builds llama.cpp from scratch each time.
