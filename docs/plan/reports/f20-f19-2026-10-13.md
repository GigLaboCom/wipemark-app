# Acceptance F20 and F19 — report, 2026-10-13

**Коротко, для владельца.** Ollama с Gemma 4 (импорт GGUF) отдаёт ответ
модели в поле `message.thinking`, а `message.content` оставляет пустым, если
в запросе не сказано `"think": false`. Wipemark этого не говорил, поэтому
все 48 ответов в задании 18 были пустыми, считались ошибками движка
(`engine`), а строка всё равно читалась как готовая («Частично
переписано»), хотя файл был очищенным оригиналом байт в байт. Теперь каждый
запрос к Ollama (`/api/chat`) несёт `"think": false` — переписываем без
рассуждений, как и локальный движок; запросы к OpenAI-совместимым серверам
не изменились. Если старый Ollama всё же пришлёт только `thinking`, это
отдельная причина отказа — `empty` («ответ пуст»), а не `engine`; в журнал
пишется лишь то, что рассуждение пришло, и его длина, но не текст. Задание,
в котором ни один абзац не переписан, больше не выглядит готовым: строка в
главном окне показывает «Не переписано» (жёлтым, как предупреждение, не
зелёным) и называет самую частую причину — например, «Ничего не
переписано: все ответы движка оказались пустыми. Ничего не записано». По
вашему решению (D712) такое задание ничего не пишет: ни файла
`name.rewritten.ext`, ни текста в строке вставленного текста; строка говорит
«Ничего не записано», а «Сравнить» открывается на очищенном оригинале, а не
на переписанном тексте, которого нет. Если «Переписать снова» тоже ничего
не переписало, прежний результат остаётся на диске как был.
Агент по MCP получает ошибку (`isError`) без текста, с причиной;
`wipemark-cli rewrite` завершается с кодом 2 и ничего не пишет. Три фразы в
настройках, говорившие, что окна «пока ничего не переписывают», исправлены во
всех трёх языках, а новый тест не даст такой фразе вернуться. Ещё три фразы
обещали тактику structural «только в приложении, после подтверждения», хотя
её не запускает ни одна часть продукта; теперь они говорят, что её нет в
этой версии, и второй тест это стережёт. Осталось одно: проверить шаг A5 с
Ollama на вашей машине.

## D711a and D712, as built

* **D711a — exit 2.** Nothing is written. Through the application the MCP
  tool's error is read as every refusal is (`cli-rewrite-app-refused` with
  the server's English sentence); on the command's own road the line is the
  catalogue's (`cli-rewrite-not-rewritten`, "Nothing was rewritten: every
  answer from the engine was empty. Nothing was written, and the exit code
  is 2.").
* **D712 — nothing is written (the owner's choice, 2026-10-13).** The first
  build wrote the cleaned text as the result; the owner chose the
  alternative. The batch queue's worker writes nothing for such a job,
  file or row; the row says "Nothing was written."; Compare opens on the
  cleaning of the original; a Rewrite again that rewrites nothing leaves
  the earlier result on disk. The three surfaces agree.
* **What the sentence does not say.** The coordinator asked for the row's
  sentence to say that the row's Clean writes the cleaned text. It does not
  say so, because it would not be true: on a row whose last action was a
  rewrite, Clean is greyed on both branches. Here `why_not_clean` greys
  every recorded row ("It has been cleaned already."). On `feat` D703 keeps
  Clean greyed on a rewritten row with "It was rewritten, and a rewrite
  contains the clean — Rewrite again redoes it."
  (`queue-action-clean-rewritten`), and that reason is itself untrue for a
  not-rewritten row. Letting Clean go there is a change to Redo's rules in
  `queue.rs` on `feat` (`why_not_clean`, `clean_again`), which this branch
  does not have. **Proposed for `feat`:** a `not-rewritten` row's Clean
  goes, as Clean again to a new name of the row's own. Until then its
  greyed reason gets a true sentence, and the row's sentence can then add
  "Clean on this row writes the cleaned text".
