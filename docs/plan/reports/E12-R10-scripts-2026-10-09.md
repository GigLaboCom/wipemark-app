Two files were edited:

* **`scripts/regress.py`** gains `--export-crops DIR` on `baseline` and
  `run`. Its settings are `--crop-tool`, `--crop-planar`, `--crop-refine`
  and `--crop-pad`. It also gains the selftest case
  `export_crops_runs_the_tool_once_per_file_with_its_class`.
* **`scripts/bench/report.py`** treats a model as one more config. Its
  header describes `model.jsonl`, and §3's correlations leave out lines
  that carry `model_eval`, because those lines carry R*'s measures, not
  the model's.

One Rust file was added, as a developer example only:
`crates/wipemark-picture/examples/export_crops.rs`, registered
`[[example]] test = true` in `crates/wipemark-picture/Cargo.toml` with two
tests of its own. **Why it was needed.** The CLI's `clean --json` carries
the restoration's rectangle and measures, but not the α it divided by,
and its written file is re-encoded at JPEG 95. A crop cut from it would
put the encoder's noise under FDnCNN. So the example runs the user's path
again:

* `decode_with_planes`, then `clean_refined` with `--planar` and
  `--refine`, as the CLI was built and run;
* per restoration, it writes the same layout `recon_bench --export-crops`
  writes, with the restoration's own `PixelRect`, `sigma_base`
  (`wipemark_pixels::sigma_base`), the logo and threshold, and the
  restoration's JSON.

α is the verified finding's map (its row's or the search's), taken through
`drawn` and `resampled` at the sub-pixel rectangle. That is
`recon_bench`'s own method. For a finding whose kernel was not `Area`, it
is an approximation, and `meta.json` says so. No product code moved, and
no catalogue, settings or CLI surface changed (D162, D166).

## 2. Deviations from the step's document

1. **α for R1's files is an approximation off the area kernel** (above).
   An exact α would need the verifier's template (`template_and_noise`,
   private to `wipemark-pixels`) to be reachable from an example. That is
   a product-crate change, which is out of scope here. It is proposed in
   §5 if the host finds the difference matters.
2. **`recon_bench --export-crops` gives 64 px of context; LaMa asks for
   128.** `lama_run.py` mirror-pads the shortfall and records
   `context_px` per crop. `export_crops --pad 128` (via `regress.py
   --crop-pad 128`) gives the full 128 for real files. For the bench,
   making `CROP_PAD` an argument of `recon_bench` is a one-line change
   that was not made here (§5).
3. **The bench's `meta.json` still writes `"sigma_base": null`.** R8 did
   not fill it in. `evalkit` restates it on `input.png`, over the box of
   α's support. That box can differ by a pixel from the restoration's
   `PixelRect`. R1's crops carry the Rust value.
4. **"outline_left by chroma"** (§2.1). The JSON has no `chroma_spread`.
   A file is counted when `outline_left` holds and `chroma > 4.0`, the
   condition the chroma term needs. When the share or the step could have
   fired as well, the file is still counted; this is an upper bound, and
   the table shows how many files fall in that column. Files left by
   `smoothed`, or by the share or step alone, are shown apart and not
   counted.
5. **`w` in M_hard** (§3.3 defines it only as "pixels the inverse called
   unrecoverable"). It is read as the share of a pixel's three samples
   that are clamped, or locally off from the data by more than `4h`. So
   `w > 0.6` means at least two of three.
6. **`feather-3` feathers inward.** Weights are 1/3, 2/3 and 1 from the
   mask's edge, so M1 (byte-equal outside `M_hard`) holds for every
   variant. R10 says only "feathers the seam by 3 px and may halo".
7. **M3 is read on three of its four measures.** Step, colour step and
   texture are restated. The outline's share needs the contour energy the
   mark had before restoration, and that is not in a crop. The report
   says so on every run.
8. **The A/B's two shares.** F6 reads `no_worse_share` (preferred or
   `same`). M6 and M7 read `prefer_share` (strictly preferred), because
   the bar there is "for LaMa".
9. **M4** is read as "nothing outside the mask moved", with the
   consistency inside the mask reported. A Grok R*'s own `consistency_px`
   is about 0.24 from rounding, so it cannot be 0.

   kernels good enough? If not, the smallest change is a `#[doc(hidden)]

   would be a product crate's API. It is not done.

   It is a one-line change to an example. Should it land with R12's Grok
   bench?

   the same Rust value. It is a two-line change to `recon_bench`'s
   `export`.
4. **Q-R7**: who looks, how many, and whether the pooled share or each
   observer's share decides. The scripts report both, and the verdicts
   read the pooled share.
