   `start(JobId, Document { text, format }, Options, Arc<dyn RewriteEngine>)

## What E4-4 should know

- A job is `(JobId, Document, Options)` plus an engine; `JobId` is the
  caller's. The terminal event carries everything to persist:
  `Outcome { text, report }`, with `report.to_json()` as the stored form.
- A job has no checkpoint inside it: a `kill -9` mid-job loses that job's
  attempts. Chunks are independent (their context is the source's), so a
  resumable queue could persist per-chunk winners and re-run only the rest
  — `Prepared` is deterministic for the same text, format and budget.
- `JobHandle::cancel` is the pause primitive there is; a paused job is a
  cancelled one to be started again.

## What E4-6 should know

- **The adapter.** `start` takes `Arc<dyn RewriteEngine>`; wrap
  `EngineHandle` (deviation 10). Take `info()` once, when the job starts.
- **The executor kind** (`Executor`) and a tokens-per-second rate are the
  surface's: `has_gpu_backend()` and `n_gpu_layers` for local, `Endpoint`
  for HTTP; the rate from a Check's timing (D61 shows the price before the
  run: `job::plan(..).cost(..)`, called off the GPUI thread).
- **The base seed** is the caller's: `for_executor` gives 0, so the same
  document rewrites to the same bytes. Pick one per job and keep it in the
  report if "Rewrite again" should differ.
- **Tokens** stream for every attempt, rejected ones included; a pane that
  shows them should reset on each `Stage::Rewriting`. For two-step tactics
  the first step's tokens are the pivot translation.
- **Words for every `Rejection` and `Kept`** are the catalogue's; the JSON
  ids are formats (`kind`, `reason`, `failure`). An MCP `rewrite` should
  return `report.to_json()` (ASCII) and must say tokens it sends back
  spelled, as the rest of the server does.
- `structural` needs the confirmation in the UI (`structural_confirmed`);
  `code` is refused (`Refused::CodeNotBuilt`).
