## Deviations from the document, and why

1. **`Action::Defer(Event)`, and `Swap` means "build the engine".** Rule
   10 says busy *defers* an unload or a swap until `JobEnded`; a pure
   `decide` cannot remember that by itself, so it says so as an action and
   the host replays the held events when the last job ends. `Started`
   also answers `Swap` (in both modes) — the engine is built, not loaded,
   so a job through the handle has something to ask. `Nothing` is
   returned only when no other action applies, so the list is never empty.
2. **`Unavailable::NothingOnDuty`** — the site is `EngineHandle::complete`
   with nothing on duty (§4.4 asks it to fail with `Unavailable`; none of
   the six variants says that).
3. **`LlamaError::NoBackend { searched }`** in `wipemark-llama` (not in
   "Files touched"): the "no ggml backend registered" site was a
   `Load(String)`, and mapping it to `Unavailable::NoBackend` would
   otherwise have been a string match.
4. **`LlamaError::Inference` stays `EngineError::Protocol(message)`**, not
   `LoadFailed`: a decode failure is not a load failure. Read §4.1's "Load
   and Inference keep llama.cpp's message as detail" as "neither loses its
   words".
5. **`wipemark-engine` re-exports** `async_trait`, `CancellationToken`,
   `LoadParams` and `has_gpu_backend`, so the application names them
   without depending on `tokio-util`, `async-trait` or `wipemark-llama`.
   The app's manifest gains only `sysinfo` (workspace), so `Cargo.lock`
   moves by one line.
6. **The Check's prompt is "Count from one to twenty in words, separated
   by spaces."**, not "Reply with the single word: ready." Run against the
   real Qwen3 4B, the latter answered `ready` in **one** token, and one
   token has no speed — D54's tokens per second could never be shown.
   The count reaches the 16-token ceiling.
7. **Where the host lives:** an `Entity<EngineHost>` parked in a `Hosted`
   global (the tray's pattern), because the status bar, the Engine page and
   the menu bar read it and none of them holds the others.
8. **`log_the_duty` no longer calls `engine_for`**: building an engine
   starts a worker thread, and a log line is not a reason to. The host logs
   what it built (or the refusal) when it builds it.
9. **The status block is between the banner and the rows**, not inside a
   row: it is a state with buttons and a result, and the 240 px control
   column would wrap every sentence. The three rows are directly under
   "Who rewrites".
10. **The GGUF size** (D55, "and the GGUF size beside it") is on the
    Engine page; the status bar shows the measured RAM only.
11. **`Preferences::new` takes the handle** (an eighth argument, under an
    `allow(clippy::too_many_arguments)` with a reason): the server starts
    inside it and must hold the handle from startup.
12. **Tests beyond §5:** `a_checked_model_is_unloaded_by_itself_after_the_idle_span`
    and `unload_now_waits_for_the_running_check` (`#[gpui::test]`, the
    executor's clock — the execution half the live check could not reach),
    `a_real_model_answers_the_check_and_gives_its_memory_back` (ignored,
    `llama-native`), `the_local_block_shows_memory_only_when_it_was_measured`,
    `a_check_reports_what_it_measured`, `an_endpoint_is_not_served_from_here_yet`,
    `a_load_is_measured_against_the_ram_only_where_the_ram_is_the_pool`,
    `the_server_holds_the_engine_it_was_given`, `a_check_shows_at_most_eighty_characters`,
    `the_idle_span_is_the_row_in_minutes`, `the_handle_crosses_threads`.
13. **"A second or so after launch" holds only on a steady launch.**
    `Started` waits for the scan, and the scan of a freshly placed GGUF
    hashes it once (2.5 GB took ~82 s in this unoptimised debug build);
    with the stamp written, a later launch is a `stat`.
14. **The live check of §4.9 was only partly possible** — see below.

## The live check (§4.9)

One launch, 20:15:48, `WIPEMARK_DATA_DIR=$S/e22/data` (the GGUF
hard-linked to `models/qwen3-4b-instruct-2507-ud-q4/`, rows
`models.rewrite = "qwen3-4b-instruct-2507-ud-q4"`, `engine.serves =
"machine"` — the spelling is `machine`, not `machine_only` —
`engine.local.keep = "resident"`, `ui.setup.done = true`),
`cargo run -p wipemark-app --features llama-native -- --settings=engine`.

What the log showed:

* 20:15:50 — ggml registered `CPU` (the gpu probe ran with the scan).
* 20:17:12 — the scan landed (it verified the freshly linked 2.5 GB file
  once — ~82 s in a debug build) and the host answered at once:
  `event=Started actions=[Swap, Load]`, "engine built for the rewrite
  duty … lock=false available_mb=Some(32024)".
* 20:17:14.7 — "model loaded … elapsed_ms=2371", then "local model loaded
  elapsed_ms=2414 resident_mb=Some(4623)".
* `ps -o rss=` at 2 min 10 s: **4 734 256 kB**. No `WARN` or `ERROR` line
  in the whole run.

**What could not be done: anything on screen.** The desktop session was
locked (`org.gnome.ScreenSaver.GetActive` → `true`); a capture of the
Settings window returned the lock screen. No click was sent and nothing
tried to unlock it. So the status bar's sentence, the **Check** button,
**Unload now** with the RSS before/after, and the one-minute idle unload
were **not seen in the running window**. The application was killed after
2 min 10 s; `ss -ltn | grep 5056` was empty and no `wipemark` process
remained. It was not launched a second time.

What stands in for the unseen half, all in the gates:

* the Check's request and the unload's memory on the real model —
  `a_real_model_answers_the_check_and_gives_its_memory_back` above: load
  2.6 s, 16 tokens ("one two three … fourteen…"), RSS 4371 MiB loaded →
  65 MiB after `unload`;
* the host's execution with a clock — `#[gpui::test]`s: a check loads,
  answers, arms the timer, nothing happens at 30 s, the model is unloaded
  at 61 s; **Unload now** during a running check is deferred and done when
  it ends, and a resident model arms no timer;
* the status bar's four sentences — `the_status_bar_says_who_is_on_duty`.

## What E2-3 and E4 should know

* **E2-3** plugs in at `duty::engine_for`'s `Performer::Endpoint` arm and
  at `EngineHost::swap`, which today files an endpoint as `Slot::Elsewhere`
  (`EngineHandle` answers `NotImplemented(ENDPOINT_NOT_YET)`). `decide`'s
  `Load`/`Unload` are no-ops for anything but a local engine; an HTTP
  engine's `warmup` (a connection test) would make `Load` meaningful for it
  too — decide then whether "loaded" is the word the status bar should use.
* **E4** runs jobs through `EngineHandle::complete`: it counts busy and
  sends `JobStarted`/`JobEnded`, so the idle timer and the deferrals work
  for it unchanged. The handle the MCP server holds is
  `Supervisor::engine()`. The Check is not a template for a rewrite: it has
  no Layer A and no guards.
* **Memory pressure** (D51's last clause, D55) is not built: a macOS
  dispatch source → `Event::UnloadAsked`-like event for on-demand only.
* The estimate is still not RSS: `available_mb` is total RAM where RAM is
  the pool, and the measured figure here was 4.4–4.6 GB for a 2.5 GB file
  at `n_ctx` 8192.
* `Runtime::init` now runs early (with the first scan), so a GPU pack's
  extra directories (E10) must be passed before that scan, or there.
