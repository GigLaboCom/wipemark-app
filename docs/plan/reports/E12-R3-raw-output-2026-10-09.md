## In one paragraph

`wipemark-picture` reads a JPEG's planes through upstream `zune-jpeg`'s raw
output now, and its quantisation tables through the fork's one getter.
The fork is pinned at `e8d24f7e` as a **git dependency**, not the
`[patch.crates-io]` the task wrote — the patch made Cargo downgrade `image`
(our JPEG encoder) and GPUI's image stack, because `image` 0.25.10 takes
`zune-jpeg` **0.5.15**, not the 0.4.21 R3's page said. On every fixture the
planes, the tables and the RGB raster are R3's **byte for byte**; the
bench's 832 results are R3's to the field; the cost is ×1.43 of a plain
decode against R3's ×1.40, after a crop of mine that first cost ×1.8 was
fixed. What moved is the decoder itself — 112 upstream commits — which
changes nothing any fixture of ours shows, but decodes three of upstream's
odd-sampling test images differently (bug fixes) and an 8-bit **lossless**
JPEG that 0.5.15 refused (a question for the owner, Q-R3d).

**Deviation 1 — a git dependency, not `[patch.crates-io]`.** With the
task's lines (both crates patched at the rev, every requirement of ours
`"=0.5.16-rc2"`), `cargo` resolved — by downgrading:

```
 Downgrading image v0.25.10 -> v0.25.8      (zune-jpeg 0.5.15 -> 0.4.21, zune-core 0.5.3 -> 0.4.12)
 Downgrading tiff v0.11.3 -> v0.10.3

 Downgrading ravif v0.13.0 -> v0.11.20

      Adding zune-jpeg v0.5.16-rc2 (https://github.com/GigLaboCom/zune-image?rev=e8d24f7e…)
```

and asked to keep `image` 0.25.10 (`cargo update -p image@0.25.8 --precise 0.25.10`)
it refused: *"failed to select a version for `zune-jpeg` … required by
package `image v0.25.10` … versions that meet the requirements `^0.5.5`
are: 0.5.15, … all possible versions conflict with previously selected
packages … `zune-jpeg v0.5.16-rc2 (…GigLaboCom/zune-image?rev=e8d24f7e…)`"*.
A patched package stands in for crates.io's, and Cargo keeps one package
per crates.io semver slot (`0.5`); `image` asks for `^0.5.5`, which the
pre-release does not match, so `image` had to leave the slot. That moves
our JPEG **encoder** (`image`'s `JpegEncoder`, E12-4) and GPUI's image
stack (`moxcms` is its colour management) — exactly what the task wanted
"untouched". A git source is a package of its own and shares no slot: the
lock gains the fork's two packages, our four crates move to them, and
**nothing else moves** (`git diff 33a2c0e 6a9346c -- Cargo.lock`: the
fork's `zune-core 0.5.3` and `zune-jpeg 0.5.16-rc2` added, four edges of
ours moved to the latter, `image`'s `zune-core` line spelled with its
source now that two exist; no package removed or changed in version). The `version = "=0.5.16-rc2"`
makes Cargo check that the rev carries the version the pin was written for.
Should the owner prefer the patch and the downgrade, it is the two lines of
the task in place of the workspace line, and the four manifests back to
`"=0.5.16-rc2"`.

**`zune-core`.** No crate of ours names it; the code reaches it as
`zune_jpeg::zune_core`, which is the fork's (the git `zune-jpeg` takes it
by path from the same rev). `image`, `tiff` and crates.io's `zune-jpeg`
0.5.15 keep crates.io's `zune-core` 0.5.3. Two `zune-core` 0.5.3 packages
are in the graph and never meet: nothing of ours hands a crates.io
`DecoderOptions` to the fork's decoder, and `scripts/check-zune-pin.sh`
refuses a member that names `zune-core`.

**Requirements.** The task named `wipemark-picture` and the dev-dependencies
of `wipemark-pixels` and `wipemark-image`; `apps/wipemark-cli` has one too

### The speed

`examples/planes_speed.rs` over the 21 stickers at 2048 × 2048, q95 4:2:0
(Watchword `wipemark-gemini-stickers-2026-10-04`, sha256 `5a54435b…1f04`
checked, saved by `mkset.py` with Pillow 12.3.0 / libjpeg 6.2), median of
7, summed; the two roads interleaved three times by
`E12-R3-raw-output-against-r3.sh` (load average 4.9–5.9 — the host was not
idle; each road's three ratios agree to 0.5 %):

| round | this road: `decode` | with planes | ratio | R3's road: `decode` | with planes | ratio |
|---|---|---|---|---|---|---|
| 1 | 622.2 ms | 890.6 ms | ×1.431 | 615.0 ms | 863.3 ms | ×1.404 |
| 2 | 622.7 ms | 891.1 ms | ×1.431 | 614.0 ms | 864.0 ms | ×1.407 |
| 3 | 617.5 ms | 885.2 ms | ×1.434 | 607.5 ms | 856.6 ms | ×1.410 |

(the "decode" column is `planes_speed`'s "old" — `decode` as at
`4b5ba17`, on each road's own decoder; per file, round 1: this road ×1.403–
×1.471, 22–33 ms → 31–46 ms; R3's ×1.388–×1.434.) The RGB decode costs the
same on 0.5.16-rc2 as on 0.5.15; the planes add about 19 ms more over the
21 files than R3's patch did (268 against 249 ms, round 1). **×1.43 against R3's ×1.40**: D491's routing
stands (only `decode_with_planes` takes them).

`examples/planes_cost.rs` (new) says where it goes, summed over the 21:
`zune-jpeg`'s RGB `decode()` 224.2 ms; raw headers + `decode_into_planes`
203.2 ms; the crop and `Plane::new` 43.2 ms; `wipemark_picture::decode`
616.0 ms; `decode_with_planes` 860.5 ms. **A finding of my own making:**
the first crop, `chunks_exact(stride).take(height).flat_map(..).collect()`,
cost **308.4 ms** — more than the decode — and put the road at ×1.80
(`planes_speed`, 1079.1 / 600.1 ms) before anything else was looked at:
a `flat_map` has no length for `collect` to allocate by, and the copy does
not vectorise. Row by row into a `Vec` allocated once is 43 ms.

## What upstream's raw output does differently — for R6 and R8

1. **The planes are the same bytes** (all our fixtures; the IDCT, its
   clamping and the progressive path agree with R3's patch). R6 can build
   on `Planes` as R3 described it.
2. **Tables by value, not by slot.** The getter hands out each component's
   table in SOF order, natural order, `u16`; no slot index, so `Quant`
   cannot say which DQT slot a table came from (nothing needs it) and Cb/Cr
   "share" a table when the values are equal. R8 reads the values, which is
   what the interval needs.
3. **No `restart_interval`, no `progressive` flag.** R3's `JpegPlanes` had
   both; `Planes` never carried them. If R8 needs either, it reads the
   markers (as `tests/planes.rs`' `header` does) — raw output does not say.
4. **The padding is in the buffer, and undocumented.** Raw output fills
   `stride × allocated_height`; upstream calls what lies past the logical
   size implementation-defined. Whether it holds what the RGB path's
   upsampler reads at an even edge (R3's Finding 1) was not checked here,
   and nothing promises it, so `Planes` crops it and Q-R3a stands as it
   was.
5. **A DNL-height JPEG** gets no planes (raw output refuses it before
   decoding); its RGB raster is still read.
6. **The raw session** switches the decoder to incremental mode for its
   lifetime and back on drop; a decoder used for raw output is not reused
   for pixels by us, so this does not show.
7. **`Sampling::Other`** — the generic upsampler's edge rows changed
   upstream (#482), and `to_rgb` is 40 edge pixels off by up to 2 on #482's
   picture. If R6 restores anything but the four named samplings, it needs
   a test there first.
8. **x86-64.** Measured here through the NEON paths, and held on CI's
   x86_64 runner through AVX2 by the same tests (see CI): the restatement
   and the planes are the same integers on both.

## Beyond the planes: the decoder moved

`decode` — every surface's road — now runs upstream `dev`, 112 commits past
0.5.15 in `crates/zune-jpeg`. Nothing of ours moved (the raster table, every
picture suite, the CLI's and the MCP server's image tests, the bench). Two
things did on inputs no fixture of ours has:

* **Odd samplings decode differently** (the three upstream rows in bold
  above) — upstream bug fixes. Not a sampling a generator hands out.
* **An 8-bit lossless JPEG (SOF3) decodes now.** 0.5.15 refused it (*"The
  library cannot yet decode images encoded with Lossless Huffman encoding
  scheme"*); upstream added it in `23de4803`. Our scan walk passes SOF3
  through as `NotWalked`, so `jpeg_decode` now hands back its raster as
  `Fidelity::Lossy`, and a proved mark on one would be restored and
  re-encoded at JPEG quality 95 — a lossless file written back lossy —
  where it used to be "pixels not examined". No fixture has one and Pillow
  cannot write one, so it is untested here; it is Q-R3d. Arithmetic coding
  stays refused (upstream's `arith` feature is off by default and nothing
  here turns it on).
