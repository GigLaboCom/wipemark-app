## Для владельца

**F1.** Загрузка модели теперь пишет в журнал. На каждый файл одна строка
в начале: модель, файл, только хост сервера (без пути, без параметров
запроса и без токенов), ожидаемый размер, и продолжается ли загрузка, с
какого байта. Дальше строки хода загрузки: байты, проценты и скорость в
МБ/с. Первая такая строка пишется на первом байте. Следующая не раньше,
чем пройдут и десятая часть файла, и 30 секунд; две строки никогда не
идут в пределах одной секунды. Конец загрузки тоже попадает в журнал. В
итоге на файл выходит не больше дюжины строк. В конце одна итоговая
строка: «проверено» (размер и секунды), «не совпала» (по 12 знаков
ожидаемого и полученного хеша, уровень warn), «отменено» или «ошибка»
(вид ошибки, HTTP-статус и причина в сети, уровень warn). Если сервер
продолжил загрузку с нужного байта, это тоже пишется. Если сервер
проигнорировал запрос на продолжение и отдал файл целиком, это тоже
пишется. `wipemark-cli models pull` идёт через тот же код и пишет то же.
**F7.** SIGTERM, SIGINT (Ctrl-C) и SIGHUP теперь завершают приложение тем
же путём, что «Выйти» в трее. Снимается маяк `mcp.json` и сокет
`wipemark.sock`. Модель выгружается, и приложение дожидается этого.
Настройки сохраняют своё окно. В журнале строка `quitting on SIGTERM`.
Второй сигнал во время выхода завершает процесс сразу, с кодом 128 + номер
сигнала. Так зависший выход всё равно можно прервать из терминала. Есть и
вторая страховка: `SIGKILL` перехватить нельзя, поэтому маяк, оставленный
мёртвым процессом, убирается при следующем запуске, и об этом тоже пишется
в журнал. `--version` и CLI не изменились. Живую проверку с `kill -TERM`
я не делал (приложение не запускал); её делает координатор, шаги ниже.

## What was built, by file

### D715, D716 — the downloader's lines (`crates/wipemark-models/src/store.rs`)

- **`should_log(now, done, total, last)`** (`store.rs:153`) is the pure
  throttle, D716. It always says the first byte. After that, a line waits
  for another tenth of the file **and** 30 s since the last line
  (`LOG_EVERY`), whichever comes later. The end is said without waiting
  for either, once. No two lines come within a second (`LOG_AT_MOST`), and
  that includes the end. `Logged { at, done }` is the last line.
- **`FileLog`** (`:250`) is one file's account. It writes the start, the
  server's answer to a resume, progress through `should_log`, and exactly
  one end (`ended` guards it): verified, unchecked (no sha256 in the
  catalogue), mismatched, cancelled or failed. It holds only the
  catalogue's model id and file name, and the URL's host from
  `host_of` (`:226`, `ureq::http::Uri::host`, so no path, query or port).
- **`Wire`** (`:172`) puts what went wrong on the wire into words and
  numbers. It takes `ureq::Error` (`status` with the HTTP code, `timeout`,
  `host not found`, `connection failed`, `io`, `tls`, `redirect`,
  `stalled`, `other`) or a body read's `io::Error` (ureq's error inside
  it, or `read` and the I/O kind). An error's message is never logged,
  because it carries the URL.
- **`StoreError::kind`** (`:490`, public) gives the error in a word. These
  are the same words `wipemark-cli`'s `kind_of` logs a pull's end with.
- **`fetch`** (`:1093`): a refusal outside any one file is one `warn`
  `a download failed` with `model` and `kind`, through `refused`
  (`:241`). That covers an unusable id, a folder that cannot be made, no
  room, and a `meta.json` that cannot be written after the last file.
  `fetch_one` (`:1159`) now owns the file's `FileLog` and writes the
  failed or cancelled end for any error the body left unsaid. The old body
  is `fetch_file` (`:1182`), unchanged except that it hands the log down
  and says *mismatched* and *verified* or *unchecked*. `download`
  (`:1294`) says the start, the answer to a resume, each chunk's progress
  and the end, and the wire's failures with their cause and status.
- The test server (`Server::answering`) can now answer a `302` to a path
  on itself, the way Hugging Face does to its CDN.

### D718 — the stale beacon (`crates/wipemark-models/src/beacon.rs`, `apps/wipemark-app/src/mcp/server.rs`)

- **`Beacon::remove_if_dead`** (`beacon.rs:137`) removes a beacon whose
  process does not run (`Beacon::alive`, the CLI's own check) and returns
  what it named. It reads the file again just before removing it, so a
  beacon another instance wrote in between stays. A beacon whose process
  runs (this one or another) stays, and so does a file that is not a
  beacon.
- **`sweep_beacon`** (`server.rs:605`) is the supervisor thread's first
  act (`:632`). It runs before any command, so before this run writes its
  own beacon, and whether or not the server is on. It writes
  `MCP: a beacon left by a process that no longer runs is swept` with
  `pid` and `port`.
- **What already happened.** A stale beacon was *replaced* when this run's
  server started on loopback: `leave_beacon` (`server.rs:585`) calls
  `Beacon::write`, which renames over the old file. It stayed when the
  server was off (the default), failed to start or was bound off loopback.
  None of those cases wrote a log line. So the sweep is new, and so is its
  test.

### D717, D719 — signals (`apps/wipemark-app/src/signals.rs`, `main.rs`, `Cargo.toml`)

- **`signals::quit_on_signals`** (`signals.rs:83`) starts a thread,
  `wipemark-signals`, which registers SIGTERM, SIGINT and SIGHUP through
  `async_signal::Signals`. Its handler, in the signal's context, only
  writes the signal number to a socket pair (`signal-hook-registry`
  underneath). The registration happens on that thread: if the thread
  could not start, the signals keep their default action. Otherwise they
  would be registered with nobody reading the pipe, and swallowed for
  good. `arrivals` (`:105`) reads them with `futures_lite::future::block_on`.
- **`watch`** (`:127`) hands the first signal to the GPUI side over a
  `flume` channel. A later signal, while the quit runs, logs a `warn` and
  ends the process with **`_exit(128 + n)`** (`end_now`, `:156`, one
  `unsafe` line). The same happens to a first signal when nothing on the
  GPUI side is left to hear it.
- **`hear`** (`:166`) is a foreground task. For each signal it writes
  `quitting on SIGTERM` (or `SIGINT`, `SIGHUP`) at `info`, then calls
  `App::quit`, the call the tray's Quit makes (D344). So every
  `on_app_quit` handler runs: the beacon goes (`take_beacon_at_quit`), the
  socket goes (Linux), the model is dropped and waited for, Settings
  saves its rectangle, and the tray is taken down.
- **`main.rs`**: `#[cfg(unix)] mod signals;` (`:90`) and the call, first
  thing in the run closure (`:1546`). That is after `--version` has
  printed and returned (`:1412`) and after a summons was handed to a
  running instance (`:1434`). Nothing else in `main.rs` changed.
- **Dependencies.** `async-signal = "0.2"`, `futures-lite = "2"` and
  `libc = "0.2"` were added under `[target.'cfg(unix)'.dependencies]` in
  the app's `Cargo.toml`. All three were already in `Cargo.lock`
  (0.2.14, 2.6.1, 0.2.189). They were already built for this binary
  through gpui-component's `smol` (`async-process` → `async-signal`) and
  gpui itself. The lock gains three edges in `wipemark-app`'s list and no
  package. Why not the two crates the task named:
  - **`ctrlc`** (with `termination`) does not say which signal came. The
    log line names it, and the exit code is 128 plus its number.
  - **`signal-hook`** is not in the lock; only `signal-hook-registry` is.
    `async-signal` is the safe wrapper over that registry that the lock
    already holds.

## Readings, and where I chose

1. **"Whichever comes later" read as both.** D715 says progress comes
   "at most once every 10 % of the file **or** every 30 s, whichever comes
   later, and never more than once a second". I read "at most … whichever
   comes later" as a rate limit, so a line waits for both a tenth and
   30 s. Under the other reading (either one is enough), the one-second
   floor would only matter between 10 % steps. Under this reading it
   matters at the end, so the end is held back by the floor (a file that
   comes down in under a second says its first byte, and the verified line
   follows). Every property the test lists is then a separate thing that
   goes red on its own. If the owner wants a line at least every 30 s
   instead, it is one operator in `should_log` (`&&` → `||`), and the
   test's two "not enough" cases flip.
2. **Mismatched at `warn`.** D715 names `warn` for *failed* only. A
   mismatch is a failed download from the person's side (the page shows an
   error, and the bytes are thrown away). The crate already logs a stale
   file's mismatch at `warn`. Lowering it to `info` is one macro.
3. **No retry line, because there is no retry.** The downloader has never
   retried a dropped connection. It ends as `a download failed`
   (`kind=transport`, `io=…`) and keeps the `.part`. The next Download or
   `models pull` resumes it: its start says `resume=true from=<byte>`, and
   the server's 206 is `a download resumes where it stopped from=<byte>`.
   Adding an automatic retry would change behaviour, which is beyond
   D715's "says what it does".
4. **A model the person added (E8-1) is never downloaded.** It is a file
   already on the disk, so "logs the same way" has nothing to apply to.
   Every download there is goes through `fetch`.
5. **D719 and the CLI.** The CLI gets no handler from this task. Its own
   Ctrl-C handler for `models pull` (`apps/wipemark-cli/src/models.rs:733`,
   `ctrlc`) is older than this task and was left as it was.
6. **`_exit` is one `unsafe` line in the app**, which already has others
   (`display_watch.rs`, `pasteboard.rs`). `std::process::exit` would run
   C++ static destructors on the way out, and with a loaded model that
   includes llama.cpp's Metal teardown. A quit that hangs is exactly when
   that is unwanted.
