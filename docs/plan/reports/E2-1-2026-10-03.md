## Deviations from the document, and why

1. **`llama_log_set` was not mnemoria's.** §4.3 says "mnemoria does
   this; keep it". It does not: no `llama_log_set`/`ggml_log_set` call
   exists in any `.rs` file of heretic-mnemoria at `a160f8c` (searched
   the whole repository, `target/` and vendored trees excluded). It is
   new code here (`ffi::install_log`, installed before any backend load,
   load or header read). And errors go to `tracing` at **warn**, not
   debug: the reason a load failed is only in llama.cpp's log, and at
   debug it would not reach the log file at the default filter.
   Everything else is debug, as asked.
2. **`wrapper.h` includes `gguf.h`.** §4.2 lists three headers. The
   `gguf_.*` allowlist of the same section binds nothing without it, and
   `estimate` reads the GGUF header through it.
3. **The C++ is built `Release` whatever cargo's profile.** Not in the
   document; found by the live gate. The `cmake` crate maps cargo's dev
   profile to `CMAKE_BUILD_TYPE=Debug`, and the first live run decoded at
   **1.4 tokens/s**. `CMAKE_BUILD_TYPE` in the environment still wins.
4. **One decode thread per physical core.** Not in the document. The
   copied code left llama.cpp's C default (4 threads); the first fix,
   every logical CPU, measured 6.4 tokens/s on 12 threads against
   **10.4** on 6. Physical cores come from sysfs `thread_siblings_list`
   on Linux (llama.cpp `common`'s rule), logical CPUs elsewhere, capped
   by `available_parallelism`.
5. **Backends: first directory wins, never `ggml_backend_load_all()`.**
   §4.3 names the three directories and their order, which is what
   `search_dirs` returns. The copied code also called
   `ggml_backend_load_all()`, which searches ggml's compiled-in
   directory, the executable's directory **and the current working
   directory**; that call is gone. And ggml registers the same backend
   twice when two directories carry it, so a later copy is unloaded
   again (`ggml_backend_unload`). Only the single-directory case is
   exercised on this machine; the de-duplication has no test that could
   go red here (see "Unfinished").
6. **`GGML_BACKEND_DL` and `GGML_BACKEND_DIR` are not passed through**
   from the environment (every other `GGML_*` is, each named in a
   `cargo:warning`): they decide the shape of the library this crate
   links, and a value from the environment produces one it cannot use.
   A `cargo:warning` says it was ignored.
7. **`kv_bytes_per_token`/`kv_cache_mb` take a `KvShape`.** §4.3 writes
   `kv_cache_mb(n_ctx, kv)`. The copied functions assumed one Gemma-sized
   shape for every model; the shape now comes from the model's own
   header, and `KvShape::COARSE` (the copied constant) is the fallback.
   `MemEstimate` gained `kv_shape: Option<KvShape>` — `None` says the
   fallback was used.
8. **`estimate` in a shim build refuses `NotBuilt`** (after refusing a
   missing file). Reading the header is llama.cpp's; a shim estimate from
   file size and a guessed shape would be a number nobody could trust.
9. **The shim `Model` is uninhabited** (`Infallible`), so "return `Ok`
   from the shim" cannot be written as a plain `Ok(Model { … })`. The
   mutation was performed as `Ok(Model { never: todo!() })` (red) and
   with two compilable variants (below).
10. **`ContextOverflow` when the prompt leaves no room**: `used >=
    limit`, not only `used > limit` — a prompt of exactly `n_ctx` tokens
    cannot generate one token.
11. **Fixes to the copied code** (each named in the provenance header and
    in `local-engine.md`): a sampled token is accepted once
    (`llama_sampler_sample` already accepts at this pin — the header wins;
    mnemoria's second `llama_sampler_accept` counted every token twice in
    the penalty window); the context is dropped before the weights
    (mnemoria's field order freed the model first); there is no fallback
    "gemma" chat template (a wrong template produces fluent text — now a
    refusal); the prompt is decoded in `n_batch` batches with the flag
    read between them (mnemoria's one-batch prompt hit
    `GGML_ASSERT(n_tokens_all <= cparams.n_batch)` — a process abort —
    past 2 048 tokens).
12. **Surface additions** (the shape is §4.3's): `Runtime::get`,
    `Runtime::dirs`, `search_dirs`; `BackendKind` is this crate's own
    enum with an `Other`; `sampling_of` and `TOP_K` are `pub`.
13. **`wipemark-engine` depends on `tracing`** (non-optional): the worker
    logs lengths and timings. §4.4's manifest lists only `wipemark-llama`.
14. **The sys crate has `links = "wipemark_llama"`** (needed for the
    `cargo:backends_dir=` metadata §4.2 asks to keep) and exports
    **`BACKENDS_DIR`**: `cargo:rustc-env` reaches only the crate whose
    build script emits it, so `wipemark-llama` could not `option_env!`
    `WIPEMARK_LLAMA_BACKENDS_DIR` itself.
15. **The native suites.** The cancel test fires 1 s after the **first
    streamed piece**, not 1 s after the request: on this CPU the first
    piece arrives ~1 s in (prefill and first-step setup), and a cancel at
    1 s after the request landed at the end of the prompt — correct
    (63 ms), but not the gate. `wipemark-llama/tests/native.rs` also has
    `the_estimate_reads_the_models_own_shape` and `the_live_gate_figures`,
    and its `the_runtime_reports_at_least_the_cpu_backend` is **not**
    ignored (it needs no model, so native gate 2 runs it). None of the
    nine gates runs that file's ignored tests; they were run separately
    (below).
16. **A queued request's cancel does not wait for the one ahead.** §4.4
    says: when the token fires, "set the flag and await the reply
    anyway". Done literally, a request queued behind another caller's
    waits for that whole generation before its cancel returns — 28.6 s
    in the test below. The reply is still awaited whenever the worker had
    taken the job up (the reason §4.4 gives); a second flag, `started`,
    tells the two cases apart without a lock (the argument is in
    `complete`'s doc comment). New native test:
    `a_queued_request_is_cancelled_without_waiting_for_the_one_ahead`.
17. **`docs/README.md`** gained an index row (not in "Files touched").
    `docs/plan/README.md` has no E2 status table; the status is the
    "Series" line of its E2 section, now *done*.

## What E2-2 should know

* **Construction.** `LocalEngine::new(LocalConfig { model_id, weights,
  load, available_mb })` spawns the worker and loads nothing; `warmup`
  loads. Hand it the catalogue id, the verified weights path
  (`State::Present` only), `LoadParams { n_ctx: entry.ctx_default, .. }`.
* **`available_mb` is E2-2's decision**, and the estimate is not RSS. On
  this CPU one load at `n_ctx` 4096 peaked at 4.16 GB against an estimate
  of 2 429 + 306 MiB: llama.cpp's compute buffers and its CPU repack copy
  of the weights (`use_extra_bufts`) beside the mapped file pages are not
  estimated. A Gemma 3 estimate errs the other way (every layer counted
  at the full window though its sliding-window layers are not).
  `None` refuses nothing.
* **`Runtime::init` — the first call wins.** If E2-2 wants extra backend
  directories (a user's GPU pack), it calls `Runtime::init(&dirs)` before
  the first load; otherwise `Model::load` initialises it with the three
  default places. It dlopens fourteen CPU variants to score them, so call
  it off the GPUI thread like everything else here.
* **Refusals are English `Display` strings in `EngineError::Unavailable`**
  ("built without llama.cpp…", "no model file at …", "the model needs
  about … MiB and … MiB is available", llama.cpp's own load messages).
  They are for logs. The catalogue sentences are E2-2's; if a surface
  needs to tell the three apart, `Unavailable(String)` is the place to
  make structured — `LlamaError` already is.
* **A panicking worker is permanent**: the engine then answers
  `Unavailable("the local engine's worker has stopped")` until it is
  rebuilt. Nothing in the normal path panics; a llama.cpp `GGML_ASSERT`
  aborts the process regardless.
* **Timing on a CPU**: about a second to the first piece of a short
  prompt, 10 tokens/s after (Ryzen 5 2600X). A cancel costs one decode
  step. Only Qwen3 4B was run; the catalogue's Gemma 3 12B (and its chat
  template, which now must be recognised or is refused) has not been.
* **Building the app with `--features llama-native`** compiles llama.cpp
  (≈ 2 min the first time) and needs `vendor/fetch.sh` first. A debug
  build of the app now carries a Release llama.cpp.
* **Stderr stays clean**: llama.cpp's log is routed to `tracing` before
  the first backend load, so nothing of it reaches stderr; it reaches the
  log file only through a subscriber installed before the engine is
  touched, which both `main`s do first thing (`wipemark_log::init`).

## Unfinished, stated as unfinished

* **The backend de-duplication** (a backend present in two search
  directories is loaded from the first and unloaded from the second) has
  no test that can go red on this machine: only one directory has
  backends here. It was not mutated. It needs a second directory with a
  copy of the CPU libraries, which a test could build from
  `BACKENDS_DIR` — left for E2-2 or E10, whichever first ships backends
  next to the executable.
* **No live gate on Metal or CUDA** (OV §10 asks for both); this machine
  has neither toolkit. `GGML_CUDA=ON` and Metal are wired through the
  environment passthrough and the macOS defaults but were not built.
  Vulkan was tried once on this machine's GPU and worked (above); it is
  not a gate.
* **No CI lane builds `llama-native`** (§7, by design).
