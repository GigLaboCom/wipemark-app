## Deviations from the document, and why

1. **A transparent character is checked before "word character".** §4.2
   defines both terms, and the two overlap. The four Hangul fillers
   (U+115F, U+1160, U+3164, U+FFA0) are letters, finding-capable, and of
   `Script=Hangul`. Some marks are finding-capable too: variation
   selectors, U+034F. Read literally, a filler would be a *voting letter*
   that `clean` may remove, and removing it would change a word's script
   between passes, which is exactly the hazard H1 exists to close. §4.2
   also says transparent characters "are never looked at", so they are
   skipped first and never vote. The doc comment on `is_transparent`
   says this.
2. **One extra unit test, `a_medial_sigma_in_a_latin_word_is`**
   (`rσom`, §4.6's edge-case row). It goes red under U02 (sources only:
   U+1D0F) and U01.
3. **`nothing_is_replaced_without_aggressive` also walks the 16
   `Options`.** Under every one of them, the text changes only with
   `aggressive`, and the text is always suspicious. The reason is
   practical: `tests/common/mod.rs`'s `every_options` is `pub` in a
   module each test crate compiles, and a test crate that does not call
   it fails clippy's `dead_code` under `-D warnings`.
4. **`homoglyph_replacement_is_idempotent` counts before it asserts.**
   (a) and (b) are evaluated under both option sets, and one assertion at
   the end reports "x of 39 inputs and y of 10000 strings". Without that,
   H1, H4 and H5 fail on a hand-written input first and the corpus count
   never prints. The integration test keeps its own copy of the §5.1
   inputs, because the unit test's constants are not visible from
   `tests/`.
5. **`ALPHABET` is `#[rustfmt::skip]`**, so it keeps §5.2's grouping
   (Latin, Cyrillic, Greek, the rest); rustfmt would reflow it.
6. **Small documentation edits outside the "one line / one expression"
   scope.** These are the crate doc sentence in `lib.rs` ("Homoglyph
   detection (E1-4) and the five guards (E1-5) are not here yet" was
   false at HEAD), the `scrub.rs` module doc, and the two stale lines in
   layer-a.md's Scrubber section. No code outside the seam changed.

The module map and the interfaces of README §3.2–3.3 are unchanged:
`homoglyph::hits(text: &str) -> Vec<Hit>` is the only new
`pub(crate)` item. CLAUDE.md and the document do not disagree anywhere.

## What the next documents should know

- **E1-6.** `p U+0430 y` gives one row, `{"codepoint":"U+0430",
  "class":"homoglyph","confidence":"probable"}`. It is in `kept`
  (`action: keep`) without `aggressive` and in `findings` (`action:
  replace`) with it, and `suspicious` is true either way (D4). That
  makes the CLI exit code 1 for a homoglyph even without `--aggressive`.
  This is D3/D4 as decided, but a surface should say "found, not
  replaced" and not leave a user wondering why nothing changed. A
  prototype found in a Cyrillic word (Latin `a` in `пaрк`) is a row
  whose code point is U+0061, and `name_of` names it ("LATIN SMALL
  LETTER A").
- **E1-6 / owner.** The replacement is what the eye sees: U+043A
  becomes U+0138 (kra), not `k`; U+03B2 becomes ß. A reader who expects
  "the ASCII word" will be surprised, and the surfaces should not
  promise ASCII.
- **E1-7.** `tables.rs`'s module-wide `dead_code` allowance is still
  needed by the five functions and five statics listed above.
- **Anyone touching `homoglyph.rs`.** Under `nfkc`, E1-3's rounds hide
  a pass that is not idempotent, so a regression in H1–H5 shows only
  under `aggressive` alone. Keep that option set in the idempotence
  gate.
