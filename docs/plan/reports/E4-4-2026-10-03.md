## What was built

1. **A resumable job beside `start`** (`crates/wipemark-pipeline/src/job/`):
   `start_resumable(id, document, options, engine, carried: Vec<Decided>)`.
   `start` is now `spawn(…, None)` — the same job, no new event, no new
   JSON key. A resumable job emits `Event::ChunkDecided { job, chunk,
   decided }` for every chunk it decides (rewritten, kept: no candidate
   passed, no tactic, marker in text), and takes `carried` back:
   `Event::Resumed { job, carried, discarded }` after planning (only when
   anything was handed in); a carried chunk is not asked, its winner goes
   into the assembly as decided, and no engine is warmed up when every
   chunk is carried.
2. **`Decided`** (`job/resume.rs`): index, the job's fingerprint, the
   chunk's digest (text, context, protected spans), the estimate, the
   outcome, the winner (placeholders and all), the report's JSON of the
   attempts and their `ChunkCounts`; `to_json` (ASCII, `"record": 1`) and
   `from_json`. `fits(chunk, fingerprint)`: same fingerprint, same index
   and estimate, same digest, outcome and winner agree, the winner still
   restores. The **fingerprint**: sha256 over a version tag, the package
   version, the format, the document's text, `Debug` of the options, of
   the engine's `EngineInfo`, of the budget and of the usable rungs (their
   templates included).
3. **The report** (`report.rs`): `ChunkReport::carried: Option<Carried>`,
   `Carried { attempts: Value, counts: ChunkCounts }`, `ChunkReport::counts()`
   (what `totals()` now sums); a carried chunk's JSON is `"carried_over":
   true` with the attempts as recorded; `outcome_value`/`outcome_of` (the
   outcome's JSON both ways), `attempts_value`.
4. **Options as a row** (`job/stored.rs`): `Options::to_json` /
   `Options::from_json` — every field, the overrides by their D74 key and
   value; a version, and an error naming the first unreadable field (never
   the defaults). `Overrides::iter` added for it (`prompt/choose.rs`, one
   method).
5. **The store, schema 2** (`crates/wipemark-store/src/{lib.rs,queue.rs}`):
   `queue (id AUTOINCREMENT, state, item, result)`, `queue_chunks (item,
   idx, record)` with `ON DELETE CASCADE`, `queue_control` (one row:
   paused). `Store::queue()` → `Queue<'_>`: `insert`, `last_id`, `rows`,
   `set_state`, `set_result`, `end` (one transaction with the chunk
   delete), `rename_state`, `put_chunk`, `chunks`, `remove`, `paused`,
   `set_paused`; `Error::Queue { what }`. `PRAGMA secure_delete = ON` on
   every connection.
6. **`crates/wipemark-queue`** (new): `Queue::open(path, engine)` (falls
   back to memory, never fails), `Queue::on(store, durability, engine)`;
   `push`, `pause`, `resume`, `cancel`, `remove`, `items`, `events`,
   `result`, `shutdown`, `durability`; `Request { source, format,
   destination, options }`, `Source::{File, Text}`,
   `Destination::{Row, File, InPlace(Keep)}` + `Destination::beside`,
   `State` (six), `QueueEvent` (`Added`, `Started`, `Job`, `Ended`,
   `Interrupted`, `Removed`, `Paused`, `Resumed`, `Unsaved`), `End`
   (`Done`, `Delivered`, `Failed`, `Cancelled`), `Failure`, `Unread`,
   `Undelivered`, `Written`, `ItemView`, `Shown`, `Durability`, `Refused`.
   The thread (`worker.rs`) waits on the handle's commands and the running
   job's events with one `flume::Selector`.
7. **Intake** — `text::decode`/`text::encode` and `inplace::same_file`
   moved from the CLI's `input.rs` (which now re-exports them; behaviour
   and the CLI's tests unchanged), so the queue reads and writes a file
   exactly as `clean` does.
8. **`scripts/check-dep-direction.sh`** — `wipemark-queue` classified:
   `{engine, pipeline, store, intake, log}`; added to `LIBS` (apps may use
   it). Root `Cargo.toml`: member and workspace dependency.
9. **Documents** — the plan document; "The queue" in
   `docs/architecture/pipeline.md`; this report.

Dependencies: nothing new from outside the workspace. `Cargo.lock` moved

wipemark-queue`).

## Deviations and decisions, and why

| # | what | why |
|---|---|---|
| 1 | **A new crate, `wipemark-queue`**, rather than the pipeline with a storage trait or the app. | Reading a file needs intake's decoding and writing one needs `inplace`; the pipeline may reach neither (core, engine only) nor the store. In the pipeline it would have been three one-implementation traits with the real behaviour testable only in the app; in the app it would be dead code until E4-6, the `kill -9` gate would link GPUI, and the CLI could never reach it. A crate costs one row in the dependency script. |
| 2 | **The whole job is invalidated, not a chunk**, when the fingerprint moves (source, options, engine, budget, templates). | A report whose chunks were decided under two sets of rules lies about both. The per-chunk digest is a second check (a record filed under the wrong chunk), not a way to keep part of a changed job. |
| 3 | **A carried chunk's attempts stay JSON** (`ChunkReport::carried`), not typed `Attempt`s. | An attempt carries core's `CleanReport`; core has zero dependencies and a writer but no reader. The final JSON carries the attempts exactly as recorded and the totals count them; a typed reader (`report.chunks[i].attempts`) sees an empty list for a carried chunk and `carried` beside it. |
| 4 | **`start` emits nothing new**; `ChunkDecided` and `Resumed` only from `start_resumable`; `"carried_over"` only where true. | The bench (E4-5) drives `start`; its event stream and JSON are byte for byte what they were. `ChunkReport` did gain a field — a struct literal of it outside the pipeline would no longer compile (none exists in this branch). |
| 5 | **Options are stored per item** (`Options::to_json`), and an unreadable row fails the item. | A per-run "two candidates" (D61) or a confirmed `structural` (D73) must survive a restart rather than become the defaults. |
| 6 | **The queue executes a destination; it reads no Retention row.** `Row` for text; `File(beside)` or a chosen path; `InPlace(Keep)` only as pushed. | The rows are the window's (Retention rule 3 keeps the CLI off them); E4-6/E7 turn them into a `Destination`. Keeping text under `kept/` is also theirs. |
| 7 | **Two-phase delivery** (`delivering`), and `End::Delivered` for a delivery finished at the next open. | A crash between "the file is written" and "the row says done" must neither lose the result nor fail an in-place item on its own set-aside original. `Delivered` carries no typed report: the report is in the row (`Queue::result`). |
| 8 | **Ids are allocated in the handle** (an atomic seeded from `sqlite_sequence`), the row is inserted on the thread. | `push` must not touch the database on the caller's thread. One queue per database: two processes running queues over one file would collide on ids — the application owns the queue, the CLI opens the database read-only (out of scope, §7). |
| 9 | **A pasted text lives in its row until the item is removed**; `secure_delete` overwrites what is removed. | There is nowhere else to take a paste up from after a restart. The WAL may hold a copy until its next checkpoint — said in the architecture document, not promised away. |
| 10 | **Pause is a row** (`queue_control`), not a settings key. | A paused batch stays paused after a restart; it is state, not a preference (CLAUDE.md, "A preference belongs in Settings"). |
| 11 | **A failed database write is `QueueEvent::Unsaved`**, and the queue goes on in memory. | The work in hand is worth more than the row; the surface says it will not survive a restart. Not gated by a test (a write failure mid-run needs a disk that fills). |
| 12 | **The `kill -9` gate is not platform-gated.** | `Child::kill` is `SIGKILL` on Unix and `TerminateProcess` on Windows; both are abrupt. Run on Linux only. |
| 13 | **Found by the gate: a busy loop.** The handle shows a pushed item as `Queued` at once; the thread picked it before its `Push` arrived, found no request, and looped without reading its inbox — at 100 % CPU, forever. `next_waiting` now considers only items the thread has. | The `kill -9` gate failed 2 runs in 5 with "the child recorded no two chunks in a minute"; the child's queue thread was at 100 % CPU. Mutation Q15 below. |
| 14 | **A reader that opens the database while its creator is switching it to WAL** makes the switch fail (the store logs a warning and runs in rollback-journal mode). | Seen while writing the gate (its parent polls the file); the gate waits for the `-wal` file before it reads. A product consequence only if the CLI opens a brand-new database in the instant the app creates it; noted, not fixed. |

## The `kill -9` gate's evidence

`crates/wipemark-queue/tests/kill.rs`, `the_queue_survives_kill_9`: the
test binary re-executes itself on the ignored `kill_9_child` with the
scratch folder in `WIPEMARK_QUEUE_KILL_CHILD`. The child opens a queue
over `<scratch>/wipemark.db`, pushes `notes.txt` (six paragraphs, six
chunks) with `Destination::beside`, on a `FakeEngine` that swaps each
paragraph's first two words at 15 ms a word. The parent polls the file
read-only (after the `-wal` exists), sends `SIGKILL` once two chunk rows
are there, and asserts: the child did not exit by itself; the row is still
`running`; fewer than six chunk rows; no result beside the file. It then
opens the queue on the same file with an instant engine and asserts the
item resumes by itself, the engine is asked for exactly the paragraphs
without a row, in order; the result (event and `notes.cleaned.txt`) equals
`start`'s on the same text; the source is untouched; the report marks
exactly the recorded chunks `carried`; `totals().attempts` is 6; the
chunk rows are gone.

Ten consecutive runs after the fix in deviation 13 (`cargo test -q -p
wipemark-queue --locked --test kill -- --nocapture`), each ~0.9 s, all
green, each printing:

```
kill -9 gate: 2 of 6 chunks recorded when the child was killed; 4 asked after the restart
```

Before that fix, 2 runs in 5 failed with "the child recorded no two
chunks in a minute" and a child whose `wipemark-queue` thread sat at
100 % CPU — the gate found the busy loop. Mutations Q2 (no chunk rows)
and Q3 (no `running` → `queued` at open) turn it red.

## What E4-6 should know

- **Push from a surface:** build a `Request` — `Source::File(path)` or
  `Source::Text`, the `TextFormat` from what intake said, the
  `Destination` from the Retention rows (`Destination::beside` for rule 1,
  `File(folder.join(..))` for the results folder, `InPlace(Keep::Original)`
  only from a per-run choice), and the job's `Options`. Text goes to
  `Row`; keeping a copy under `kept/` is the surface's.
- **The engine** is one `Arc<dyn RewriteEngine>` for the queue's life —
  the `EngineHandle` adapter E4-3 described; the queue does not re-ask who
  rewrites between items.
- **Open the queue off the GPUI thread** (`Queue::on` with the app's own
  `Arc<Store>` and the same durability the app's config fell back to), and
  `Queue::result` too. Everything else on the handle returns at once.
- **Progress:** `QueueEvent::Job { event }` is the pipeline's stream;
  `Resumed { carried }` is "picked up at chunk n"; `ItemView::decided`
  counts. `Unsaved` and `Durability::Memory` need a sentence each.
- **Words:** every `Failure`, `Unread` and `Undelivered` variant needs one
  in the catalogue; the row's JSON carries ids (`kind`, `reason`).
- **The MCP `rewrite` tool** can push `Source::Text` with
  `Destination::Row` and read the `Done` from the event, or bypass the
  queue with `start`; the queue serialises it behind any batch.
