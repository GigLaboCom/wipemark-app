# E10 — the Linux AppImage and .deb, the MnemoVi way (2026-10-12)

**Для владельца.** Собран Linux-выпуск 0.1.0 так же, как MnemoVi: в
закреплённом Docker-образе Ubuntu 24.04, с инструментами, проверенными по
sha256. Получились два файла: `Wipemark-0.1.0-x86_64.AppImage` (43,4 МиБ) и
`wipemark_0.1.0_amd64.deb` (26,9 МиБ). Они лежат в
`.claude/worktrees/agent-a5a942bd55058121f/dist/` (ветка `e10/appimage`).
Запуск: `chmod +x Wipemark-0.1.0-x86_64.AppImage && ./Wipemark-0.1.0-x86_64.AppImage`.
Командная строка запускается так: `./Wipemark-0.1.0-x86_64.AppImage --cli inspect файл`.
Пакет ставится командой `sudo apt install ./wipemark_0.1.0_amd64.deb`. Он
добавит Wipemark в меню приложений с иконкой-метлой во всех размерах.
Проверено в чистых контейнерах Ubuntu 24.04. Командная строка работает на
голой системе и даёт ровно те коды выхода, что в таблице паритета. Окно
открывается под Xvfb, MCP отвечает, программа завершается по SIGTERM. На
своём рабочем столе ничего не запускал.

**Что посмотреть глазами.** Первое — пункт «Wipemark» в меню приложений и
его иконку (после установки `.deb`). Второе — иконку в доке и в Alt+Tab,
пока программа запущена. Сейчас там, скорее всего, будет **безымянная
стандартная иконка**. Причина в том, что наши окна не сообщают системе своё
имя (`app_id`), и GNOME не может связать окно с `wipemark.desktop`. Под
Xvfb это измерено: у окна нет `WM_CLASS`. Исправление — одна строка в
каждом из четырёх окон, текст ниже. Сам я его не вносил, потому что эти
файлы сейчас правит другой агент (заголовки окон).

## What was taken from MnemoVi, and what was not

Read at `mnemoria-lvkb` (`ci/linux-builder/`, `scripts/ci/`) and in its built
`MnemoVi_0.2.6_amd64.AppImage`, extracted.

| MnemoVi | Wipemark | why |
|---|---|---|
| a builder image, Ubuntu 24.04 **by digest**, the toolchain inside, a tag derived from the inputs, the caches mounted beside and keyed to the base | the same (`ci/linux-builder/`, D600) | "which image built this" survives a rebuild; no object built on another glibc reaches a release |
| tools pinned by sha256 (`appimage-tools.sha256`) | the same, from **versioned** URLs: appimagetool 1.9.1, type-2 runtime 20251108, rustup-init 1.28.2 (D601) | MnemoVi's `continuous` URLs moved under it; a version plus a hash is both reproducible and fetchable |
| linuxdeploy + its GTK and GStreamer plugins | **not taken** (D601) | Wipemark carries three system libraries; linuxdeploy's built-in excludelist is what MnemoVi spent `appimage-fill-excluded.sh` working around |
| `appimage-excludelist-policy` (HOST / SHIP / PURGE, a reason per soname) | the same file and format, HOST / SHIP; and **an undecided soname fails the build** (MnemoVi's reports it) (D604) | a new dependency is a decision |
| `glibc-floor.sh` with `glibc-floor` and `libstdcxx-floor` | the same, adapted (D607) | the floor is the newest symbol version any shipped ELF asks for |
| `appimage-shipped-manifest.sh` (dpkg provenance, copyright files staged) | the same idea, smaller: every file with size and sha256, the dpkg package of each carried library, its copyright file staged | the list cannot drift from the artifact |
| `linux-launch-gate.sh` — stock distro + X + EGL, a screenshot by the bundle's own ffmpeg | `appimage-gate.sh` — stock ubuntu:24.04 for the CLI; + the declared floor for the application, **Xvfb and the X tools in a second container** | Wipemark ships no ffmpeg; a screenshot tool in the app's container could satisfy a library the AppImage should carry |
| `linux-deb-install-gate.sh` and its third question | `deb-gate.sh`, the same three questions, and **Depends computed** so the third holds by construction (D608) | MnemoVi's `libgomp1` was satisfied by accident |
| `.desktop` with `StartupWMClass` = the binary's name, `glib::set_prgname` | `StartupWMClass=wipemark`; the windows' `app_id` is the matching half (D605) | the dock's join |
| `.DirIcon` → an absolute path on its build machine (dangling in the published AppImage) | a relative link | a defect not copied |
| GStreamer, WebKit, ffmpeg, ORT, ggml packs, CUDA EP gate, the GPU/model mounts | not applicable | different stack; llama.cpp comes prebuilt (`pin.rs`) |
| third-party notices from a hand-kept JSON | from `cargo metadata` (D606) | Cargo.lock already lists everything |

## The layout

```
Wipemark.AppDir/
  AppRun   wipemark.desktop   wipemark.png (256)   .DirIcon -> wipemark.png
  usr/bin/wipemark -> ../lib/wipemark/wipemark
  usr/bin/wipemark-cli -> ../lib/wipemark/wipemark-cli
  usr/lib/wipemark/   wipemark, wipemark-cli (RUNPATH $ORIGIN)
                      libllama.so.0 libggml.so.0 libggml-base.so.0
                      libggml-cpu-{14 variants}.so libggml-vulkan.so
                      libgomp.so.1 libxkbcommon-x11.so.0 libxcb-xkb.so.1
  usr/share/applications/wipemark.desktop
  usr/share/metainfo/wipemark.metainfo.xml
  usr/share/icons/hicolor/{16,22,24,32,48,64,128,256,512}x…/apps/wipemark.png
  usr/share/icons/hicolor/scalable/apps/wipemark.svg
  usr/share/doc/wipemark/  NOTICE  THIRD-PARTY.md  third-party/*.copyright
```

How llama.cpp is found (D602). The build's rpath names the builder's prebuilt
directory (`build.rs` of `wipemark-llama-sys` and of both applications);
`appdir.sh` rewrites it to `$ORIGIN` with patchelf. It refuses any other rpath.
The backends are found because `wipemark_llama::Runtime` already searches the
executable's directory first. `/proc/self/exe` is `usr/lib/wipemark/wipemark`,
not the `usr/bin` link. So no Rust change was needed. The application's log
under the gate confirms it: `ggml backends registered devices=CPU
dirs=["/tmp/appimage_extracted_…/usr/lib/wipemark", …]`.

How `wipemark-cli` is reached (D602). AppRun runs the CLI when the first
argument is `--cli`, or when the AppImage is called through a link named
`wipemark-cli` (the runtime's `$ARGV0`). Otherwise it runs the application.
The .deb has `/usr/bin/wipemark-cli`.

## The excludelist and the floor

Carried: `libgomp.so.1` (OpenMP for ggml), `libxkbcommon-x11.so.0` and
`libxcb-xkb.so.1` (NEEDED by `wipemark` before `main`, not brought by GTK).

Left to the machine:
- glibc and libstdc++/libgcc_s;
- GTK 3 with glib, gdk-pixbuf, libxkbcommon and libxcb;
- the Vulkan loader and drivers;
- libayatana-appindicator (dlopened by the tray).

The declared floor is glibc ≥ 2.39, libstdc++ ≥ GCC 13, GTK 3, and a Vulkan
loader with a driver. Measured: the newest symbol versions are `GLIBC_2.39`
(`wipemark` itself) and `GLIBCXX_3.4.32` (`libggml-vulkan.so`).
`scripts/release/linux/excludelist-policy` gives the reason for each soname.

Found while measuring:
- The application **links** GTK, so it does not start without it, not even
  for `--version`. On a bare server the loader stops at `libxkbcommon.so.0`.
  The CLI needs none of it.
- The MCP server is off by default. The gate turns it on in the database the
  first launch created, then checks the beacon.

## The icons and the app_id finding

Icons (D603). The full hicolor set comes from `icons/linux/hicolor` (16, 22,
24, 32, 48, 64, 128, 256, 512 and scalable SVG; the SVG's C2PA metadata is
already stripped there, and no PNG carries any). The 256 px icon is at the
AppDir's root and `.DirIcon` points to it. `desktop-file-validate` and
`appstreamcli validate --no-net` pass. The AppStream id is `com.giglabo.wipemark`:
AppStream refuses an upper-case domain, so `com.GigLabo` could not be used.

**The app_id (D605).**
- `grep app_id apps/` finds nothing. Every `WindowOptions` leaves it `None`.
- In `gpui-pre 0.3.8`, `Window::new` calls `platform_window.set_app_id` only
  when it is `Some` (`window.rs:2059`).
- The X11 backend writes `WM_CLASS` only in `set_app_id`
  (`gpui-pre-linux` `x11/window.rs:1597`). The Wayland backend sets the
  toplevel's `app_id` only from the option (`wayland/window.rs:594`).
- Measured under Xvfb on the AppImage: `WM_NAME "Wipemark"`, `WM_CLASS: not found`.

GNOME therefore cannot join the window to `wipemark.desktop` (on Wayland by
`app_id`, on X11 by `WM_CLASS`). The dock and Alt+Tab show a generic icon.

**The change needed, for the coordinator**
(`fix/linux-titlebar-activate` owns these files today):

```rust
// apps/wipemark-app/src/title.rs — beside the titles; one string with
// packaging/linux/wipemark.desktop (its name and StartupWMClass), the hicolor
// icon name and the binary.
/// The X11 WM_CLASS and the Wayland app_id of every window (D605).
pub const APP_ID: &str = "wipemark";
```

and in each of the four `WindowOptions { … }`:
- `main.rs` (≈1436)
- `settings.rs` (≈9434)
- `compare.rs` (≈823)
- `panel.rs` (≈198)

add

```rust
    app_id: Some(title::APP_ID.into()),
```

A test belongs with it. It would read `packaging/linux/wipemark.desktop`
(`include_str!`) and assert that `StartupWMClass=` and `Icon=` are `APP_ID`.
That way the window and the desktop file cannot drift apart. To check it,
run `scripts/verify/release/appimage-gate.sh`: the `NOTE run 1: the window's
WM_CLASS` line must change from `not found` to `"wipemark", "wipemark"`. On
the owner's GNOME desktop, the dock should then show the broom.
