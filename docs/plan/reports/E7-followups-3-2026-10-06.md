### Y1 — a panic while the plan is taken

`Cleaner::next` (`apps/wipemark-app/src/cleaner.rs`) now takes the plan
through a `plan` field (`type PlanOf = fn(&Preferences, &Intake) -> Plan`,
`Preferences::plan_for` by default — the seam D288's `run` is) under
`catch_unwind(AssertUnwindSafe(…))` on the foreground. On a panic the job
ends as a panicking clean ends: `Event::Started`, the line's `finish`,
`Event::Finished` with `clean::panicked(id)`, and the loop goes on to the
next job — so `ask` (or `finished`) returns normally and nothing is left
running.

**The catch, not the sentence.** The verifier's other answer — documenting
that a panic there ends the application — is not true: the panic unwinds
into whoever called `ask`, a click handler in either window, and the line
is left with `running` set. I found no reason to take it.

The test hands the line a plan that panics on `plan-panics.md`, asks for
it and then `after.md`: `ask` returns, the verdicts are
`[Failed(Panicked), Cleaned]`, `after.cleaned.md` is on disk, nothing is
written for the first, and the line is idle. Y1/M1 (the catch removed) is
red, not HANG: the panic escapes `cleaner.update` and fails the test.

**Probe H** (`PROBES=H scripts/verify/e7/probes.sh`, at `d6a5a60`) now
prints: "a fault in plan_for", "the panic in plan_for was caught", the
line's progress afterwards `Ok(None)`, a second clean asked `Ok(true)`,
`after.cleaned.md` written, four events heard (two `Started`, two
`Finished`).

### Y2 — D286's byte comparison pinned

`an_interrupted_delivery_is_finished_not_failed` now says what the first
name holds when the queue opens again as `Now::{Left, Written, Saved}`.
`Saved` is someone's atomic save — a temporary in the same folder renamed
over `note.md`, a new inode — never `std::fs::write`, which after a
hard-link set-aside would write through the shared inode and change the
set-aside too. Three cases more:

1. set aside by a link, then saved over with exactly
   `PARAGRAPHS[0].len()` other bytes — `Failed(OriginalExists)`, both files
   left alone;
2. the same with bytes of another length — the same end;
3. set aside by a link, then the original's very bytes saved back (another
   inode, the same bytes) — `Delivered`, as D286 intends; the test's
   comment says why.

Y2/M1 (= H41, the length for the bytes) is red on case 1. H40's and
H42's lines are untouched and their tests only grew.

### Y4 — the panel's look and the clean take one plan (D290)

`Held` keeps `plans`, the plan each listed thing was looked at by. The
panel observes `Preferences` (`replan`): on every notification it plans
the held things again — pure, no read — and for each thing not yet
cleaned whose plan moved it stores the new plan, clears the look and
looks again, one read on the background executor (D278 kept: never a
read per frame, and none for a change elsewhere, such as the panel's own
move). A look lands only while the plan it was taken by is still the
thing's, so an older look finishing late cannot overwrite a newer one. The
row is painted by the held plan, so the look, the painted row and — the
page unchanged — the clean read one plan. "Where it would go" is now the
pure `would_lines`, which the tests read.

Tests: `the_look_is_taken_by_the_plan_a_clean_would_take` (a
`link.md -> target.md` dropped under *In place*: the link refusal and no
would-lines; under *Beside*: a look and would-lines) and
`the_look_follows_a_change_of_plan` (dropped under *Beside*, then the page
switched to *In place*: the link refusal with no new drop and no
