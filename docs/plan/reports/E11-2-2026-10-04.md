## What was built

1. **The CLI takes a picture** (`apps/wipemark-cli/src/image.rs`, new).
   `input::read_any` hands over a `Picture` when intake places the bytes as
   PNG, JPEG, WebP, TIFF, HEIC or AVIF **by their contents** (`picture_of`);
   `run::inspect`/`run::clean` dispatch to it. `inspect` lists every block
   (chunk/segment, key, kind, offset, length) under "Would be removed" /
   "Would be kept", each AI block with its signals (signal, field, the
   signature that matched — never the value), a colour note, the line that
   only the metadata was examined, and the third shelf; `--json` is
   `ImageReport::to_json()`. `clean` strips (`--all-metadata` →
   `Scope::AllMetadata`), writes beside / `-o` / stdout (not a terminal) /
   `--in-place [--no-original]` through `wipemark_intake::inplace`, and
   exits by the input — **3, and nothing written, when `still_has_*`**.
   `audit` inspects pictures in all three renderings.
2. **MCP `inspect_image` and `clean_image`** (`apps/wipemark-app/src/mcp/image.rs`,
   new; `protocol.rs`). `data` is base64 (strict standard alphabet, padded);
   `scope` is `ai-provenance` | `all-metadata`. Answers are the library's
   JSON in `content[0].text` and `structuredContent`; refusals are `isError`
   results naming why. No `path`.
3. **The library's formats** (`crates/wipemark-image`): `json.rs` —
   `ImageReport::to_json`, `StripReport::to_json`, `spell` — and stable ids
   and names: `ImageContainer::{ALL, id, name}`, `MetadataKind::{ALL, id}`,
   `Signal::id`, `Defect::{IDS, id}`, `Scope::{ALL, id}`. No behaviour moved.
4. **Catalogue**, en/ru/de: `cli-arg-all-metadata`, `cli-audit-image`, 19
   `cli-image-*`, 8 `image-kind-*`, 5 `image-signal-*`, 11
   `image-defect-*`; `cli-command-{inspect,clean,audit}`,
   `cli-arg-in-place` and the MCP banner `settings-mcp-tools` ("Five tools
   run … the metadata only, never the pixels") reworded in all three.
5. **Docs**: the plan (written first), `docs/architecture/cli.md` (image
   rows in the exit table, an "Images" section, `audit`'s statuses and
   SARIF), `docs/architecture/images.md` ("JSON", "Surfaces", "Next"),
   `docs/architecture/layer-a.md`'s MCP section, the `docs/README.md` row;
   this report and `E11-2-mutate.py`.

Tests added (compiled, not run here): `tests/image.rs` 15 (the binary,
end to end, on `wipemark-image`'s own `tests/support` borrowed by `#[path]`
and its decoders as dev-dependencies); `image::tests` 6, `input::tests` 2,
`run::tests` 1 (CLI units); `json::tests` 4 (library);

## Open questions for the owner, in product terms

1. **Should an agent be able to point the MCP server at a file?** Today it
   must send the picture's bytes (up to about 750 KB). A `path` argument
   would allow large files but lets anything that reaches the server — and
   it can be bound past this machine with no password — read and overwrite
   files by name. Not built.
2. **Is camera metadata a "finding"?** Today `inspect` on a photo with only
   camera EXIF exits 0 ("nothing AI here"). A user who wants every photo
   stripped of location and camera data before publishing would want 1.
   That would be a second mode, not a change of this one.
3. **A picture that cannot be read: 2 or 3?** Chosen 3 ("not read is not
   clean", as for a text in an encoding we cannot read). The task said 2.
4. **`clean` on a picture: exit by what was there, or by what is left?**
   Chosen "what was there" (1 when provenance was removed), as text does.
5. **TIFF/HEIC/AVIF in `audit`**: skipped and listed. Should a folder full
   of HEIC photos from a phone make `audit` inconclusive (3) instead?
6. **`audit --json` consumers** read `report.suspicious` for a text; a
   picture's report says `ai_metadata`. Should the picture's report also
   carry `suspicious` (same value) so one key answers for both?
