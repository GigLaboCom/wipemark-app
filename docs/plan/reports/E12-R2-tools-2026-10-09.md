## 1. What was built

### `scripts/corpus/ring.py` — §4.1's check

* **The row**: the first placement row, in catalogue order, whose `when`
  matches the picture's size and whose rectangle fits (`--row` takes
  another). The product tries every row (`propose.rs::rows`); the catalogue
  lists the specific row before the general one, so the first that answers
  is the mark's (V1 2048 → row 0, 96 at 64; V1 1024 → row 1, 48 at 32). The
  rectangle is restated as `bias.py` and `propose.rs::row_rect` state it; a
  corner row's map size is read from the `.wma` header.
* **A resampled row is handled, not refused**: this check needs only the
  square, never `α`, and a resampling row's own `rect` is that square
  (`1376×768` → `[1232, 624, 48, 48]`, `resample: true` in the output).
  `bias.py` refuses such a row because it needs the map; this does not.
* **The ring**: 8 px outside the square, clipped at the edge. Per channel
  the mean, the standard deviation and the RMS residual of
  `calibrate.rs`'s quadratic basis.
* **The rule**: `gray-*`, `black`, `white`, `sat-*` pass when the spread —
  **the standard deviation, in every channel** — is under 8 levels
  `[tunable]`. `gradient` passes when the quadratic describes the ring
  (residual ≤ 2 levels, `SMOOTH_RESIDUAL`, `[tunable]`, new). `texture` has
  no rule; its numbers are recorded.
* **Where a failing file could go**: `gradient` (the quadratic describes
  it), `texture` (the residual is even over the ring's four sides, within
  ×3, `EVEN_SIDES`, `[tunable]`, new), else `drop` (something on one side
  is neither).
* **A label note**: a flat ring at another level than its group's (say
  `gray-50` at 190) passes with a note naming the group it looks like. §4.1's
  rule is the spread; the level is the owner's label to correct.
* `--json` gives the fields `manifest.py` records. Exits: 0 pass, 1 a file
  failed, 2 refusal.

### `scripts/corpus/manifest.py`

| command | what |
|---|---|
| `add` / `build` | rows per §4.4, with the ring check on background rows. A failing file refuses the whole run, unless `--on-fail move`, which moves it (`moved_from`) or lists it under `dropped`. A path already a row with other bytes is refused (D304); the same bytes twice are one row. `build` reads the group from the folder and the profile from the folder above (`<profile>/<group>/<file>`) |
| `verify` | `--root` or `--zip`: a file whose sha256 differs from its row is refused, and so is a missing file. The ZIP must be stored (a deflated member is refused), its own sha256 is checked against the source's, and a member no row names is attention (exit 3) |
| `zip` | a stored ZIP of one source, sorted by path, timestamps 1980-01-01, so the same set gives the same bytes. Every file's sha256 is checked before it is packed. `--key` pins the key and the ZIP's sha256, and the previous key moves to `previous`. A key is never reused for other bytes |
| `captures` | `captures.toml` in `captures.example.toml`'s shape, per profile: `black`, `white`, `gray-*` (as `grey`), sorted by size. It leaves out held-out files, failed files and files `inspect` found `unverified` or has not checked (`--unchecked` keeps those). It says when a size has no black, white or grey |
| `inspect` | §4.1's second check: `wipemark-cli inspect --json` per row (sha256 first), recorded in the row as `verified`/`unverified`. On `negative`, a `verified` is a known false positive |
| `grok` | stage 0: format, the JPEG's subsampling and DQT tables (and the IJG quality they are, exact or nearest), size and aspect, the clip's stream via `ffprobe` or "not available", plus the by-hand fields from a TOML or CSV sidecar. Renders §4.3's table, a clips table, a per-file table and the gate line. `--manifest` writes the rows; `--cli` adds C2PA/AI metadata |
| `selftest` | below |

**`held_out`, stable as the set grows.** A row's flag is decided once, when
the row is written, and never looked at again. A run's new rows are sorted by
sha256 within their stratum (the group; for Grok, source and group) and
numbered on from the stratum's existing count; the 5th, 10th … is held out.
That gives:

* a stratum always holds out ⌊n/5⌋ of its files;
* a held-out file stays held out, and a training file stays in training;
* within a run the choice is the bytes', never a listing's.

The cost: one run and two runs over the same files can hold out different
files. `batch` records the order. The manifest stores the rule
(`held_out.every`, `.by`), and `validate` refuses a manifest whose rule moved.

**No `corpus/*/manifest.json` was created.** `bias.py list` reads any
manifest with a `files` list of `path`, `sha256`, `group`, `held_out` rows,
which this schema is. `regress.py` reads `golden/manifest.json` only (the
negatives and midtone rows go there through `regress.py pin --add`). So an
empty skeleton helps neither, and it would have to name a key that does not
exist. `add`/`build --set` starts the file on first use.

**`wipemark-cli inspect --json` does not carry a JPEG's subsampling or
quantisation tables.** Checked on `fixtures/image/gemini/torch-1025-q95-420.jpg`
with the debug CLI of the main checkout: `container`, `ai_metadata`, `c2pa`,
`findings`, `visible`, `not_established`. So `grok` reads them off the SOF
and DQT markers in Python, as the brief allows. It still calls the CLI, with
`--cli`, for C2PA/AI metadata.

## 5. Questions

1. **A group of fewer than five holds out none.** "Every fifth" is taken
   literally (the 5th, 10th …), so ⌊n/5⌋. §6 accepts 3 per group, and such a
   group then has no held-out file. Should a group hold out ⌈n/5⌉ instead
   (the 1st, 6th …), at the cost of 33 % of a group of three? (owner)
2. **Batch dependence.** Stability as the set grows means the held-out choice
   depends on how the files were batched. The alternative — held out iff
   `int(sha256) mod 5 == 0` — is independent of batching but holds out 20 %
   only on average (a group of five can hold out none or three). The plan
   keeps the spec's sort; say if the other is preferred. (owner)
3. **"Spread" is read as the standard deviation per channel**, the second of
   the three numbers §4.1 lists, not max − min. Max − min over 1 700+ pixels
   of a real PNG would fail most flat corners on noise alone. (owner, at the
   first real run)
4. **Grok's corpus has two homes.** R2 §4.4 names `corpus/grok/manifest.json`.
   R12's stage 4a added `regress.py --golden golden/grok` (Grok's regression
   corpus, its own `manifest.json` in `golden/`'s schema). They hold
   different things — stage-0 facts and held-out flags against regression
   expectations — but the same files. Say whether `golden/grok/` should be
   built from `corpus/grok/` (as `golden/manifest.json` takes the negatives),
   so the two cannot disagree. (coordinator)
5. **The CLI's JSON has no JPEG tables.** If R11 or R12 wants them from the
   product rather than from a Python parser, that is a field of
   `wipemark-image`'s report and a decision. Not proposed here. (coordinator)
6. **Thresholds new in this step**, all `[tunable]` and used only by the tool:
   * `SMOOTH_RESIDUAL` 2 levels;
   * `EVEN_SIDES` ×3;
   * the level windows of the label note (dark ≤ 24, light ≥ 231, neutral
     within 12, saturated ≥ 128).

   None decides a pass of §4.1's rule except `SMOOTH_RESIDUAL` for the
   `gradient` group, which §4.1 does not define. Each should get its line
   once real files have been measured.
