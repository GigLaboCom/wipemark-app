# Redo a row — Clean again and Rewrite again — report, 2026-10-13

**Коротко, для владельца.** Строка, которую уже очистили, теперь вместо
«Очистить» показывает **«Очистить снова»**, а переписанная — **«Переписать
снова»**: и в меню «Действия», и кнопкой на самой строке. Повтор пишет
**поверх собственного результата строки** — того файла, который записан за
этой строкой (по её id в журнале), — и не создаёт новых `-<id>-2`. Поверх он
пишет, только если этот файл ещё существует, это не сам исходный файл, его
имя — одно из имён этой строки по нынешним настройкам «Хранения», и ни одна
другая строка списка не считает этот файл своим результатом. Иначе строка
получает результат под своим именем, как всегда: удалённый вручную результат
пишется заново под первым свободным своим именем, а изменённые настройки
пишут туда, куда указывают теперь. Если результат правили вручную в окне
сравнения и сохранили, повтор сначала спрашивает — «Переделать …?»,
«Переделать» или «Отмена»; без правок он идёт сразу, как первая очистка или
переписывание. Результат, записанный на место файла, не переделывается:
пункт серый и называет, как отложен оригинал. У переписанной строки
«Очистить» серое — переписывание уже включает очистку, его переделывает
«Переписать снова». «Очистить всё», «Переписать всё», очистка из панели,
`--clean=`, командная строка и MCP не изменились.

How a redo runs, end to end:

* **Clean again** — `clean_again(id)`: greyed rows and rows not "again" are
  left alone; an edited row emits `Again` and stops; otherwise
  `redo_clean`: `replacing = own_result(id)` (the row's `written()` unless
  another row records it), the line asked with `ask_with(id, arrival, tag,
  replacing, None)`, the row `Queued`. The clean takes its plan when it
  starts (D279); `publish` writes over `replacing` atomically when the plan
  still names it, it is there and it is not the source, and otherwise
  publishes the first free of the row's own names. `heard` resets the edit
  marks and writes the new end into the journal, whole.
* **Rewrite again** — `rewrite_again(id)`: greyed rows are left alone; an
  edited row emits `Again` and stops; otherwise `rewrite(&[id])`.
  `push_rewrites` hands `over` (rule 3) to the build; `claim`, off the GPUI
  thread with the tag resolved, makes `Destination::File(over)` when `over`
  is one of `Own { tag, plain: true }.names()` under the plan taken now, is
  there, is not the source and is claimed by no live item — and adds it to
  `claimed`. Delivery writes over it atomically and is replayed after a
  `kill -9` like any item. `pushed` removes the row's earlier item.

## Not done here

* **The live check, the owner's.** Clean again and Rewrite again on a
  cleaned, a rewritten and an edited row (the question, its Redo and its
  Cancel); a Compare window open on the row while it is redone — its
  "cleaned since" notice, and what its Save does afterwards; a redo after
  `kill -9`. The application was not launched.
* **What `kill -9` should show, from the code.** A Rewrite again's item is
  stored with its `Destination::File` and replayed like any item: it writes
  over the row's own result after the restart. A **Clean again** killed
  mid-way comes back *Not started* (D317's settling: a window clean left
  running waits again) — and without its link: the journal row written as
  the clean started carries no `result`, as every clean's does, so the row
  no longer names its earlier file, and its Clean is then a first one,
  which takes a name of its own beside that file. Not changed here.
* **The shell's question has no window test**: the queue's event and the
  catalogue's words are tested; `main.rs`'s `Asked` for it is not.
* **A rewrite's "went" line says "Written as"** where a clean's redo says
  "Written over the existing": `journal::rewrite_end` records
  `replaced: false` and does not know the item's destination. Not unified.
* **A redo that writes nothing loses the row's link to its file.** A Clean
  again of a source now clean (D262: an identical result is not written),
  or a Rewrite again that fails or is cancelled, ends with no result; the
  earlier file stays on disk and the row no longer names it, so the next
  redo takes the plain name if free and otherwise `-<id>-2`, beside it.
* **Bytes with no name** (an image dragged out of a browser) are named
  with a time stamp in the results folder; a Clean again of such a row
  writes a new file, the plan's name having changed (rule 4).
* The full gates and the native gates were not run (targeted tests only,
  the owner's rule of 2026-10-12); nothing under `crates/wipemark-llama*`
  changed. `CLAUDE.md`, `docs/plan/README.md` and `v1-release.md` were not
  edited.
